ユーザーが指定する固定点と `HEAD` の間の差分を、2軸でレビューします。

- **Standards**：コードはこのリポジトリの文書化されたコーディング規約に適合しているか。
- **Spec**：コードは元の課題・仕様を忠実に実装しているか。

2つの軸は互いのコンテキストを汚染しないよう、**並列サブエージェント**で実行し、その後このスキルが調査結果を集約します。

課題トラッカーは提供されているはずです。`docs/agents/issue-tracker.md` がない場合は、ユーザーに `/setup-matt-pocock-skills` の実行を伝えてください。

## 手順

### 1. 固定点を確定する

ユーザーが言ったものが固定点です（コミットSHA（コミットを識別するハッシュ値）、ブランチ名、タグ、`main`、`HEAD~5` など）。指定がなければ尋ねます。

差分コマンドを1回記録します：`git diff <fixed-point>...HEAD`（3点なので、比較はマージベースに対して行われます）。コミット一覧も `git log <fixed-point>..HEAD --oneline` で記録します。

先へ進む前に、固定点が解決できること（`git rev-parse <fixed-point>`）と、差分が空でないことを確認します。不正な参照や空の差分は、2つの並列サブエージェントの内部ではなく、この段階で失敗させます。

### 2. 仕様の出典を特定する

元の仕様を次の順に探します。

1. コミットメッセージ内の課題参照（`#123`、`Closes #45`、GitLabの`!67`など）。`docs/agents/issue-tracker.md` のワークフローで取得します。
2. ユーザーが引数として渡したパス。
3. ブランチ名または機能名に一致する、`docs/`、`specs/`、`.scratch/` 以下の仕様ファイル。
4. 何も見つからなければ、仕様がどこにあるかをユーザーに尋ねます。仕様がないと言われた場合、**Spec**サブエージェントはスキップし、`no spec available` と報告します。

### 3. 規約の出典を特定する

`CODING_STANDARDS.md` や `CONTRIBUTING.md` など、コードの書き方を文書化したリポジトリ内のものをすべて確認します。

リポジトリの文書に加えて、Standards軸には、リポジトリに文書がない場合でも適用される、Fowlerのコードスメル（_Refactoring_ 第3章）の固定集合である**スメル基準（smell baseline）**を必ず含めます。次の2つの規則が適用されます。

- **リポジトリが優先される。** 文書化されたリポジトリ規約は常に優先されます。基準ならスメルとして指摘するものを規約が認めている場合、そのスメルは抑制します。
- **常に判断を伴う。** 各スメルは「Feature Envyの可能性」のようなラベル付きヒューリスティックであり、決定的な違反ではありません。ここでの他の規約と同様、ツールがすでに強制しているものは飛ばします。

各スメルは*何であるか* → *どう直すか*という形で書かれています。差分と照合します。

- **Mysterious Name**：何をするか、何を保持するかが名前から分からない関数、変数、型。→ 名前を変更する。正直な名前が付けられないなら、設計が曖昧です。
- **Duplicated Code**：変更内の複数のハンクまたはファイルに同じロジックの形が現れる。→ 共通する形を抽出し、両方から呼び出す。
- **Feature Envy**：自分のデータよりも別のオブジェクトのデータに多くアクセスするメソッド。→ メソッドを、それが欲しがっているデータの側へ移す。
- **Data Clumps**：同じ少数のフィールドやパラメーターがいつも一緒に移動する（生まれたがっている型）。→ 1つの型にまとめて渡す。
- **Primitive Obsession**：独自の型を持つべきドメイン概念の代わりに、プリミティブや文字列を使っている。→ 概念に専用の小さな型を与える。
- **Repeated Switches**：同じ型に対する同じ `switch` / `if` の連鎖が変更全体で繰り返される。→ ポリモーフィズム、または両方の箇所で共有する1つのマップに置き換える。
- **Shotgun Surgery**：1つの論理的変更のために、差分内の多くのファイルへ散在した編集が必要になる。→ 変更されるものを1つの module（モジュール）に集める。
- **Divergent Change**：1つのファイルまたは module が、互いに無関係な複数の理由で編集される。→ それぞれの module が1つの理由で変わるよう分割する。
- **Speculative Generality**：仕様にないニーズのために、抽象化、パラメーター、フックを追加している。→ 削除し、現実のニーズが現れるまでインラインに戻す。
- **Message Chains**：呼び出し側が依存すべきでない、長い `a.b().c().d()` のナビゲーション。→ 最初のオブジェクトに1つのメソッドを置き、その中に移動を隠す。
- **Middle Man**：ほとんど次へ委譲するだけのクラスや関数。→ それを取り除き、実際の対象を直接呼び出す。
- **Refused Bequest**：継承したものの大部分を無視または上書きするサブクラスまたは実装者。→ 継承をやめ、コンポジションを使う。

### 4. 2つのサブエージェントを並列で起動する

**Standardsサブエージェントへのプロンプト**には次を含めます。

- 完全な差分コマンドとコミット一覧。
- ステップ3で見つけた規約ソースのファイル一覧、**およびステップ3のスメル基準全文**（サブエージェントはそれ以外から基準にアクセスできません）。
- 次の短い依頼：「関連する場合はファイルまたはハンクごとに報告する。(a) 差分が文書化された規約に違反するすべての箇所を挙げ、規約（ファイルとルール）を引用する。(b) 気づいた基準スメルがあれば、その名前を示し、ハンクを引用する。明確な違反と判断事項を区別する。文書化された規約への違反は明確な違反になりうるが、基準スメルは常に判断事項であり、文書化されたリポジトリ規約は基準より優先される。ツールが強制するものは飛ばす。400語未満。」

**Specサブエージェントへのプロンプト**には次を含めます。

- 差分コマンドとコミット一覧。
- 仕様のパスまたは取得した内容。
- 次の短い依頼：「報告する。(a) 仕様が求めた要件のうち、欠けているか部分的なもの。(b) 差分にある、依頼されていなかった振る舞い（スコープクリープ）。(c) 実装されているように見えるが、implementation（実装）が間違っているように見える要件。各指摘について仕様の行を引用する。400語未満。」

仕様がない場合、Specサブエージェントをスキップし、最終報告にそのことを記録します。

### 5. 集約する

2つの報告を `## Standards` と `## Spec` の見出しの下に、逐語的または軽く整えて提示します。2軸は意図的に分けられているため、結果を**統合したり再順位付けしたりしないでください**（_2軸である理由_を参照）。

最後に1行の要約を付けます。各軸の指摘数と、各軸**内**で最も重大な問題（あれば）を示します。軸をまたいで単一の勝者を選ばないでください。分離を設けた目的に反する再順位付けになるためです。

## 2軸である理由

ある変更は、一方の軸には合格し、他方には不合格になることがあります。

- すべての規約に従っているが、間違ったものを実装しているコード → **Standardsは合格、Specは不合格。**
- 課題が求めたことを正確に行っているが、プロジェクトの慣例を壊すコード → **Specは合格、Standardsは不合格。**

別々に報告することで、一方の軸が他方を覆い隠すことを防ぎます。
