# ドメイン文書

コードベースを調査するときに、エンジニアリングスキルがこのリポジトリのドメイン文書をどう利用するかを示す。

## 調査前に読むもの

- リポジトリルートの **`CONTEXT.md`**、または
- ルートに存在する場合はリポジトリルートの **`CONTEXT-MAP.md`**: コンテキスト（context）ごとに1つの `CONTEXT.md` を指す。話題に関係するものをすべて読む。
- **`docs/adr/`**: これから触る領域に関係するADRを読む。マルチコンテキストのリポジトリでは、コンテキスト単位の判断として `src/<context>/docs/adr/` も確認する。

これらのファイルが存在しない場合は、**黙って処理を続ける**。不在を指摘したり、先に作成するよう提案したりしない。`/domain-modeling` スキル（`/grill-with-docs` と `/improve-codebase-architecture` から呼び出される）が、用語や判断が実際に確定したときに遅延して作成する。

## ファイル構成

単一コンテキスト（single-context）のリポジトリ（大半のリポジトリ）:

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

マルチコンテキスト（multi-context）のリポジトリ（ルートに `CONTEXT-MAP.md` がある場合）:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← システム全体の判断
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← コンテキスト固有の判断
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 用語集の語彙を使う

出力でドメイン概念を名前として使うとき（課題タイトル、リファクタリング提案、仮説、テスト名など）は、`CONTEXT.md` で定義された用語を使う。用語集が明示的に避けている同義語へ逸脱しない。

必要な概念がまだ用語集にない場合は、リポジトリで使われていない言葉を発明している（考え直す）か、本当に不足している（`/domain-modeling` に記録する）という合図である。

## ADRとの矛盾を示す

出力が既存のADRと矛盾する場合は、黙って上書きせず、明示的に示す:

> _ADR-0007（イベントソースの注文）と矛盾するが、…という理由で再検討する価値がある。_

## 全体要求・設計・作業資料

要求・構成・技術選定に関わる作業では、存在する `docs/spec.md`、`docs/architecture.md`、`docs/tech-stack.md` の関連部分も読む。文書がない場合は作成を前提条件にせず、会話・計画・課題にある合意済みの範囲を使う。

### 各文書の責務

- `CONTEXT.md`：ドメインの用語とその意味。
- `docs/adr/`：リポジトリに影響する重要な設計判断とその理由。
- `docs/spec.md`：プロジェクト全体の合意した要求・受け入れ条件・制約・未決事項。
- `docs/architecture.md`：合意した目標構成と処理の流れ。MermaidまたはASCII図を含め、未実装と確認済み実装を区別する。
- `docs/tech-stack.md`：主要技術の用途・採用理由。正確な導入バージョンは設定ファイルを参照する。
- `docs/work/`：個別作業の範囲・実装手順・チケット・調査記録。配置は `docs/agents/issue-tracker.md` に従う。

### 全体文書と作業の契約

全体文書は `/to-spec` が作成し、以後は関連箇所を更新する。`/to-plan` で判断が確定した場合は、存在する全体文書の関連節へ同期する。用語集へ要求や実装手順を入れず、ADRは重要な判断の理由を残す役割を保つ。

全体仕様の完成形と、今回実装する範囲を区別する。計画・チケットには対象範囲、対象外、受け入れ条件、関連する仕様の節へのリンクを記す。仕様書がなければ合意要件を作業資料に記録する。全体文書に `ready-for-agent` を付けず、未決があれば下書きであることと影響する範囲を示す。

更新前に既存文書を読み、合意済みの判断・コードから確認できた事実・提案や未決を区別する。現状のコードだけを要求の合意の根拠にしない。無関係な節と人の編集を保持し、要求の参照に使う見出しはむやみに変更しない。

未合意の矛盾は既存の合意を残して明示する。`/to-spec` は質問せず未決として保存し、`/to-plan` は未解決の判断だけを1問ずつ確認する。既に合意した変更は聞き直さず、全体文書と作業資料の関連箇所をそろえる。同期の完了を確認できるまで、その計画を準備済みと扱わない。

実装時は着手前の合意要件・受け入れ条件を保持し、レビューの基準として渡す。検証後に全体文書へ反映する実装状況は、要求・目標の本文と分けて根拠を付ける。要求そのものの変更には合意の根拠を示し、同じ変更のレビュー対象に含める。
