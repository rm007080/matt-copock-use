# ドメイン文書

コードベースを調査するときに、エンジニアリングスキルがこのリポジトリのドメイン文書をどう利用するかを示す。

## 調査前に読むもの

- リポジトリルートの **`CONTEXT.md`**、または
- ルートに存在する場合はリポジトリルートの **`CONTEXT-MAP.md`**: コンテキスト（context）ごとに1つの `CONTEXT.md` を指す。話題に関係するものをすべて読む。
- **`docs/adr/`**: これから触る領域に関係するADRを読む。マルチコンテキストのリポジトリでは、コンテキスト単位の判断として `src/<context>/docs/adr/` も確認する。

これらのファイルが存在しない場合は、**黙って処理を続ける**。不在を指摘したり、先に作成するよう提案したりしない。`/domain-modeling` スキル（`/grill-with-docs` と `/improve-codebase-architecture` から呼び出される）が、用語や判断が実際に確定したときに遅延して作成する。

## ファイル構成

単一コンテキスト（single-context）のリポジトリ（大半のリポジトリ）:

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

マルチコンテキスト（multi-context）のリポジトリ（ルートに `CONTEXT-MAP.md` がある場合）:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← システム全体の判断
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← コンテキスト固有の判断
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 用語集の語彙を使う

出力でドメイン概念を名前として使うとき（課題タイトル、リファクタリング提案、仮説、テスト名など）は、`CONTEXT.md` で定義された用語を使う。用語集が明示的に避けている同義語へ逸脱しない。

必要な概念がまだ用語集にない場合は、リポジトリで使われていない言葉を発明している（考え直す）か、本当に不足している（`/domain-modeling` に記録する）という合図である。

## ADRとの矛盾を示す

出力が既存のADRと矛盾する場合は、黙って上書きせず、明示的に示す:

> _ADR-0007（イベントソースの注文）と矛盾するが、…という理由で再検討する価値がある。_
