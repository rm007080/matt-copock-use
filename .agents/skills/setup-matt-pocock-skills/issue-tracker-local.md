# 課題管理：ローカルMarkdown

全体要求の正本は `docs/spec.md`。作業ごとの計画・実装課題・調査課題は、同じ**作業フォルダー**にまとめる。文書の責務と更新条件は `docs/agents/domain.md` を参照する。

## 配置

```text
docs/work/YYYY-MM-DD-NN-<work-slug>/
  <work-slug>-implementation-plan.md
  issues/<NN>-<slug>.md
  discovery/map.md
  discovery/issues/<NN>-<slug>.md
```

- 計画は `/to-plan` を使う場合だけ作る。実装課題だけ、調査記録だけの作業も認める。
- `issues/` は実装課題、`discovery/` は Wayfinder の調査・判断の記録。必要なものだけ作成する。
- 作業名・課題名はASCIIの小文字英数字とハイフンを使う。作業フォルダーと課題ファイルの日付・番号プレフィックスは、命名規則の合意済みの例外とする。

## 作業フォルダーの特定と作成

作業資料を取得・保存するコマンドは、次の順で対象を決める。

1. ユーザーが指定した作業フォルダー、計画、課題、マップのパスから所属する作業フォルダーを特定する。
2. 指定がなければ、会話で合意した作業フォルダーを再利用する。作業名だけの場合は既存資料の目的・範囲も照合する。
3. 複数候補がある、または新しい作業か継続か不明なら、1問で確認する。最新の日付だけで選ばない。全体の `docs/spec.md` だけから特定の作業を推定しない。
4. 新しい作業と確定し、最初の資料を保存する段階でフォルダーを作る。`/to-plan`、`/to-tickets`、`/wayfinder` のいずれが最初でも同じ規則を使う。

`YYYY-MM-DD` は実行環境のローカル日付によるフォルダー作成日。`NN` は `docs/work/` 内の同じ日付の全作業を調べ、既存最大番号に1を加える。初回は `01`、最低2桁で、数値として比較する。同日・同番号は作業名が違っても再利用しない。既存の場所を上書きせず、新規作成の衝突時は一覧を読み直して次の番号にする。

作成した名前は固定する。未着手用の仮名、開始時の名前変更、再開・改訂時の再採番は行わない。同じ作業の計画は既存ファイルを読み、手編集・完了済みの事実・無関係な内容を保持して更新する。結果には実際の作業フォルダーと成果物へのリンクを示す。Markdownの相対リンクは、書き込んだ文書の親ディレクトリを基準に解決し、リンク先の実ファイルと参照する節の存在を確認する。コード表記でプロジェクト相対のパスを記す場合は、その基準を明示する。

作成・更新・実装開始・完了の日時は、時差を含めて計画本文に記録する。計画がない実装では対象チケットに記録する。未着手・未完了はその旨を示し、日時を推測しない。名前が表すのは登録順であり、実装順ではない。内容・Status・チェック欄・コメントを変更して保存するたびに、更新日時を現在時刻へ更新する。作成日時と最初の実装開始日時は保持する。

## 実装課題の公開と取得

「課題管理先に公開する」と指示された場合は、対象作業の `docs/work/YYYY-MM-DD-NN-<work-slug>/issues/<NN>-<slug>.md` に1課題1ファイルで保存する。仕様書は課題として公開せず、全体の `docs/spec.md` に置く。

- 初回の課題番号は依存順に `01` から付ける。再実行時は既存の課題・コメント・完了条件を読み、同じ課題を無条件に作り直さない。追加分だけ既存最大番号の次を使い、既存番号を変えない。
- `Blocked by:` に同じ `issues/` 内の依存課題の番号と名前を記す。他の作業を参照する場合は曖昧な番号だけでなく文書へのリンクを使う。着手順はファイル名だけでなく、この依存関係で判断する。
- `/to-tickets` の生成票は `Origin: to-tickets` を持つ。計画への参照は存在する場合だけ付け、計画ファイルの新設を要求しない。
- 対象範囲、受け入れ条件、対象外、関連する全体仕様の節または合意の出典を、チケット単体でも理解できる形に記す。
- コメントは `## Comments` の下へ追記する。完了した受け入れ条件はチェックし、完了日時を記録する。依存先の完了確認ではこの記録を読む。

「該当するチケットを取得する」と指示された場合は明示されたパスを読む。番号だけで複数の作業・種類に該当するなら、作業名またはパスを確認する。

## 準備状態と探索範囲

`Status:` は `docs/agents/triage-labels.md` の値を使う。計画・実装課題の `needs-info` は対象作業に必要な情報・判断・文書同期が不足している状態、`ready-for-agent` は対象範囲の要件と受け入れ条件が確定した状態。準備済みでも、実際の着手には `Blocked by` の依存先が完了している必要がある。進捗と完了はチェック欄・日時で示す。

全体仕様に残る、対象作業と無関係な未決事項は停止理由にしない。対象に関係する未決・矛盾・未同期がある場合、`/to-tickets` は新しいフォルダーやチケットの作成・更新・公開前に停止し、`/implement` は着手前に停止する。仮のチケットを作らず、未決内容を会話で返す。

通常のトリアージの自動探索は、`docs/work/*/issues/` の受付課題を対象にする。`Origin: to-tickets` の生成票、計画、`discovery/` の調査課題は除外する。ユーザーが明示指定した課題はその指示に従う。報告者の追加情報を待つトリアージと、内部計画の判断待ちを混同しない。

## Wayfinding operations

`/wayfinder` は同じ作業フォルダーを使用し、探索資料を次の場所に置く。

- マップ：`docs/work/YYYY-MM-DD-NN-<work-slug>/discovery/map.md`。
- 子課題：同じ `discovery/issues/<NN>-<slug>.md`。マップと実装計画は別の成果物であり、計画を自動作成しない。
- マップには Destination、Notes、Decisions so far、Not yet specified、Out of scope を記載する。
- 子課題の `Type:` は `research`、`prototype`、`grilling`、`task`。未取得の課題は `Status:` を未設定にし、取得時に `claimed`、解決時に `resolved` とする。これは探索専用の状態で、トリアージの5分類に追加しない。
- `Blocked by:` は同じ `discovery/issues/` 内の番号を指す。実装用 `issues/` と番号・依存関係・状態を混ぜない。
- 着手可能な課題は、未取得・未解決で、依存先がすべて `resolved` のもの。番号が最小のものを優先し、作業前に `Status: claimed` と担当者を保存する。
- 解決時は `## Answer` と根拠を追加して `Status: resolved` とし、マップの Decisions so far に要約とリンクを追記する。マップ外と判断した課題は、その理由を Answer と Out of scope に残して閉じ、Decisions so far には含めない。

引き渡すときは作業フォルダーとマップへのリンクを返す。後続の `/to-spec`・`/to-plan` は、マップから関連する決定票をたどって確定事項を確認する。未決は対象への影響を残し、確定事項として実装へ渡さない。工程間の接続は文書リンクで表し、調査票を実装票へ変換しない。

## 旧形式と保存の制約

旧パスが明示指定された場合は読み取ってよい。旧形式への新規保存や自動移動は行わず、保存先が不明なら対象作業を確認する。Planモードでは書き込みを行わず、案と未保存であることを示す。保存失敗時は実際に保存できたもの・未保存のものを区別して報告し、完了と宣言しない。
