# Improve Codebase Architecture

アーキテクチャ上の摩擦を明らかにし、**deepening opportunities（深化の機会）**、つまりshallow module（浅いモジュール）をdeep module（深いモジュール）に変えるリファクタリングを提案する。目的はテスト容易性とAIによる案内のしやすさである。

このコマンドはプロジェクトのドメインモデルを踏まえ、共有する設計語彙を基盤とする。

- 「codebase-design」でSkillツールを呼び出し、アーキテクチャの語彙（**module（モジュール）**、**interface（インターフェース）**、**depth（深さ）**、**seam（継ぎ目）**、**adapter（アダプター）**、**leverage（てこ）**、**locality（局所性）**）とその原則（削除テスト、「interfaceがテストの対象面である」、「adapterが1つなら仮のseam、2つなら本物」）を使う。すべての提案でこれらの語を正確に使い、「component」「service」「API」「boundary」にずらさない。
- `CONTEXT.md` のドメイン言語は良いseamに名前を与える。`docs/adr/` のADRは、このコマンドが再検討すべきでない決定を記録する。

## プロセス

候補選択や記録確認も含め、質問が必要なときは `grilling` の「Step 1: 入力を理解する」「Step 3: 1問ずつグリルする」「Step 4: 終了する」を参照する。原則1問ずつ、判断には推奨案と短い理由を添えて回答を待つ。短い確認ではこれらの事実確認・質問進行・終了のルールだけを適用し、Step 2の観点一覧を使う設計インタビューは始めない。候補の設計を検討するループは手順3で始め、そこで4段階全体を使う。

### 1. 探索する

**スキャンする前にスコープを決める: YAGNI。** moduleのdeepeningは、その後の変更を簡単にする。だから最近変更されたコードに重みを置く。見る前にどこを見るかを決める。

- ユーザーが方向（module、サブシステム、痛点）を指定したならそれに従い、以下の推測を飛ばす。
- それ以外は、コミット履歴（`git log --oneline`）を十分な範囲までさかのぼり、何度も現れるコードベースのホットスポット、ファイル、領域を見つける。そのパスを最初に見る。変更が散らばり明確なホットスポットがなければ、対象を広げる。

まず、プロジェクトのドメイン用語集（`CONTEXT.md`）と、触れる領域にあるADRを読む。

次に、サブエージェントを起動してコードベースを歩かせる。固定的なヒューリスティックには従わず、有機的に探索し、摩擦を感じる場所を記録する。

- 1つの概念を理解するのに、多数の小さなmoduleの間を行き来する必要があるのはどこか。
- interfaceがimplementationとほぼ同じ複雑さを持つ **shallow** なmoduleはどこか。
- テスト容易性のためだけに純粋関数が抽出され、本当のバグは呼び出し方に隠れている（**locality**がない）のはどこか。
- 密結合したmoduleがseamをまたいで漏れているのはどこか。
- 現在のinterfaceを通してテストされていない、またはテストしにくいコードベースの部分はどこか。

shallowと思うものには削除テストを適用する。削除すると複雑さが集まるのか、それとも単に移動するだけなのか。「集まる」が答えなら、それが求めるシグナルである。

### 2. 候補をHTMLレポートとして提示する

自己完結型のHTMLファイルをOSの一時ディレクトリに書き、リポジトリに何も残さない。`$TMPDIR` から一時ディレクトリを解決し、なければLinuxでは `/tmp`、Windowsでは `%TEMP%` にフォールバックする。各実行で新しいファイルになるよう、`<tmpdir>/architecture-review-<timestamp>.html` に書く。ユーザー向けに開き（Linuxでは `xdg-open <path>`、macOSでは `open <path>`、Windowsでは `start <path>`）、絶対パスを伝える。

レポートはレイアウトとスタイルにTailwindをCDN経由で使い、グラフ・フロー・シーケンスが構造を確実に伝える場合の図にMermaidをCDN経由で使う。Mermaidと手作りのCSS/SVGビジュアルを組み合わせる。関係がグラフ形状（呼び出しグラフ、依存関係、シーケンス）ならMermaidを使い、編集的なもの（質量図、断面図、統合アニメーション）なら手作りのdiv/SVGを使う。各候補には**変更前 / 変更後の視覚化**を付ける。視覚的にする。

各候補には次の内容を持つカードを描画する。

- **ファイル**: 関係するファイル / module
- **問題**: 現在のアーキテクチャが摩擦を生む理由
- **解決策**: 何が変わるかの平易な英語での説明
- **利点**: localityとleverage、そしてテストがどう改善するかで説明する
- **変更前 / 変更後の図**: shallowness（浅さ）とdeepening（深化）を示す、横に並べた手作りの図
- **推奨の強さ**: `Strong`、`Worth exploring`、`Speculative` のいずれかをバッジとして描画する

レポートの最後に**Top recommendation（最上位の推奨）**セクションを置く。最初に取り組む候補と、その理由を示す。

**CONTEXT.mdの語彙をドメインに使い、`/codebase-design` の語彙をアーキテクチャに使う。** `CONTEXT.md` が「Order」を定義しているなら、「FooBarHandler」や「Order service」ではなく「Order intake module」と書く。

**ADRとの衝突**: 候補が既存のADRと矛盾するなら、その摩擦がADRを見直す価値があるほど現実的な場合だけ提示する。カード上で明確に示す（例: _「ADR-0007と矛盾するが、…のため再開する価値がある」_）。ADRが禁じる理論上のリファクタリングをすべて列挙しない。

[HTML-REPORT.md](HTML-REPORT.md) にHTMLの完全な骨組み、図のパターン、スタイルの指針がある。

まだinterfaceを提案しない。ファイルを書いた後に、Top recommendationとその理由を短く示し、ユーザーへ「どれを検討しますか？」と1問で尋ねて回答を待つ。

### 3. 厳しく検討するループ

ユーザーが候補を選んだら、「grilling」でSkillツールを呼び出し、決定木を一緒に進める。制約、依存関係、deepened moduleの形、seamの背後にあるもの、どのテストが残るかを確認する。

決定が具体化したら副作用をその場で起こす。途中でドメインモデルを最新に保つため、「domain-modeling」でSkillツールを呼び出す。

- **`CONTEXT.md` にない概念でdeepened moduleに名前を付けるか。** その語を `CONTEXT.md` に追加する。ファイルがなければ遅延作成する。
- **会話中に曖昧な語を磨くか。** その場で `CONTEXT.md` を更新する。
- **ユーザーが候補を、重要な理由で却下するか。** `domain-modeling` のADR提案の3条件をすべて満たし、将来の探索者が同じ候補を再提案しないために記録が必要な場合だけ、理由を添えてADRとして記録するか尋ねる。「今は価値がない」のような一時的な理由や自明な理由は飛ばす。
- **deepened moduleの別のinterfaceを検討したいか。** 「codebase-design」を呼び出し、その並列サブエージェントによる「2回設計する」パターンを使う。
