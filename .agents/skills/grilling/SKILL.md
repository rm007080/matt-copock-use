---

ユーザーの計画・判断・アイデアを、質問と事実調査で磨き上げる。相談の目的に必要な判断を明確にし、共通理解に到達する。

## Step 1: 入力を理解する

相談の目的、対象範囲、既に決まったことを把握する。コードベースが関係する場合は、関連するコードや文書を先に読む。事実の確認はエージェントの仕事であり、自分で調べられることをユーザーに尋ねない。

未確定の事実と、ユーザーが選ぶ必要のある判断を区別する。環境の事実（ファイルシステム、ツールなど）の調査が必要なら、サブエージェントに調べさせる。調査待ちの内容に依存する質問は保留する。回答待ちの質問がなければ、その調査に依存しない質問をStep 3の進め方で尋ねてよい。

## Step 2: 判断事項を洗い出す

内部で、今回の目的に必要な未決の判断と、その前提となる判断・事実を整理する。これを**設計ツリー（design tree）**と呼ぶ。各判断から、それに依存する判断が枝分かれする。

次の9観点を、見落としを確認するために使う。今回の目的に関係する観点だけを検討し、この表を全項目の回答を求める質問票や、固定の質問順序として使わない。表の1行にある確認事項も、独立して答えられるものは別の判断として整理する。

| 観点 | 内部で確認すること |
|------|--------------------|
| **目的（ゴール）** | 誰が、何のために使うか。成功したと判断できる状態は何か |
| **対象範囲（スコープ）** | 今回扱うことと、扱わないことは何か |
| **利用画面・体験（UI/UX）** | ユーザーにどう見えるか。既存の使い方と整合するか |
| **データ** | 入出力や構造は何か。既存データの移行が必要か |
| **状態・同期** | どの情報を正しいものとして扱うか。同時更新や食い違いをどう扱うか |
| **例外・境界条件** | 通常と異なる条件や、失敗したときにどう振る舞うか |
| **代替案の比較（トレードオフ）** | 選択肢ごとに何を得て、何を諦めるか |
| **性能・安全性など（非機能）** | 性能、互換性、安全性、権限について必要な条件は何か |
| **導入・公開（ロールアウト）** | どう導入し、必要なら段階的に公開したり元に戻したりするか |

ユーザーがまだ考えていないが、目的達成に影響する点を探す。回答済みの内容、調査で分かること、自明な確認は質問候補から除く。**着手可能な項目（frontier）**とは、前提が揃い、未回答の判断を推測せずに今尋ねられる質問の集合である。

## Step 3: 1問ずつグリルする

着手可能な項目から、後続の判断への影響と、後から変更した場合の手戻りが大きいものを優先して、次の1問を選ぶ。呼び出し元が検討順序を指定している場合は、その順序を尊重する。たとえば幅優先なら、全体の論点を広く確認する順序を保つ。

- **1問では1点だけ扱う。** 独立した判断や事実確認を、1つの文章や選択肢に詰め込まない。閲覧範囲と編集権限も別の判断として尋ねる。ほかのスキルを併用しても、標準では対話全体で回答待ちの質問を1問に保つ。
- **判断には具体的な推奨案と短い理由を添える。** 推奨案は、その質問への回答として採用できる選択肢を示す。事実確認には推奨案を必須とせず、根拠のない回答候補を作らない。
- **使える質問ツールで尋ねる。** 現在の実行モードで利用できる選択式の質問ツールを使い、事実確認は必要に応じて自由入力にする。使えなければ文章で1問だけ尋ねる。
- **まとめて聞くのは明示依頼時だけ。** ユーザーが求めた範囲で、互いの回答に依存しない質問だけをまとめる。未回答の判断に依存する質問は回答後に扱う。この例外をほかの対話や恒久設定へ持ち越さない。

悪い例：保存先はローカルとクラウドのどちらにし、保存形式はJSONとCSVのどちらにしますか？

良い例：この端末だけで使うとのことなので、記録はローカルファイルに保存する方針でよいですか？ 現在の利用範囲を満たし、外部サービスの設定が不要なため、この案を推奨します。

1問を尋ねて回答を待つまでを**ラウンド（round）**とする。回答を得たら、先回りして答えられた内容も取り込み、Step 2の確定事項・未決事項・前提関係を更新する。不要になった質問は候補から外し、新たに必要になった判断を加えて、次の1問を選び直す。最初の質問一覧を機械的に消化しない。

判断について「分からない」と言われたら、推奨案と理由を示し、それを採用するか1問で確認する。事実が不明な場合は未確定として扱い、調査または確認できるまで、その事実に依存する判断を確定しない。

質問票やチェックリストなどの成果物に含める項目数は、この対話中の質問数の制限とは別に扱う。

## Step 4: 終了する

今回の相談の目的に必要な判断が確定し、それを左右する調査待ちがなくなったら通常終了する。次に進む支障にならない未決事項は明示して残し、解決済みとして扱わない。細部の未決事項をなくすためだけに質問を続けない。

ユーザーが途中で「ここまででよい」など終了を求めた場合は、直ちに質問を止める。通常終了・途中終了のどちらでも、次の3点を短くまとめる。

- **決まったこと**：合意した判断。
- **未決事項**：未確定の事実や判断。残っている場合は、次の作業への影響も示す。
- **次のステップ候補**：実装、プラン化、追加調査など。

終了を、実装や結果適用への承認として扱わない。途中終了時は要約して対話を終え、呼び出し元の後続処理へ自動で進まない。共通理解に達したとユーザーが確認するまでは、検討した計画を実行に移さない。用語集などの文書管理は、呼び出し元の条件と実行環境の書き込み制約に従う。
