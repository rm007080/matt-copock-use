# Prototype

プロトタイプは**問いに答えるための捨てコード**である。問いが形を決める。

## 分岐を選ぶ

確認が必要な場合は、調査で分かることと回答済みの内容を除き、原則1問につき独立した判断または事実確認を1点だけ尋ねる。現在の実行モードで使える質問ツールを使い、なければ文章で尋ねる。判断には推奨案と短い理由を添え、事実確認には必須としない。回答を待って次の確認を選び直す。ユーザーの明示依頼時だけ、その範囲で互いの回答に依存しない質問をまとめる。

判断に「分からない」と言われたら推奨案を採用するか確認する。不明な事実は未確定として扱う。終了を求められたら質問を止め、決定事項・未決事項・次のステップ候補を短くまとめる。

ユーザーのプロンプト、周辺コード、またはユーザーに尋ねることで、どの問いに答えるかを特定する。

- **「このロジック / stateモデルは妥当に感じるか」** → [LOGIC.md](LOGIC.md)。自由操作ボタンとタブ付き案内ウォークスルーを備え、紙の上では考えにくいケースをステートマシンに通し、開発者でない人が動かせる、共有可能なHTMLファイルを1つ作る。
- **「これはどう見えるべきか」** → [UI.md](UI.md)。1つのルートで、URLの検索パラメーターと画面下部に浮かぶバーで切り替えられる、根本的に異なるUIのバリエーションを複数生成する。

2つの分岐はまったく異なる成果物を作るため、取り違えるとプロトタイプ全体が無駄になる。本当に曖昧なら、周辺コードを根拠に推奨する分岐を示して確認し、回答を待つ。ユーザーに連絡できない場合は分岐を未決事項として残し、その判断に依存するプロトタイプの作成を保留する。

## 両方に適用するルール

1. **初日から捨てるものとし、そう明示する。** プロトタイプ対象のmoduleまたはページの近くにプロトタイプコードを置き、実際に使われる場所が分かるようにする。カジュアルな読者にもプロダクションではないと分かる名前を付ける。捨てるUIルートでは、プロジェクトが既に使っているルーティング規約に従う。新しいトップレベル構造を作らない。
2. **実行を簡単にする。** UIプロトタイプはプロジェクトのタスクランナーから1つのコマンドで起動する: `pnpm <name>`、`python <path>`、`bun <path>` など。ロジックのデモはユーザーがダブルクリックする1つのHTMLファイルにする。どちらも起動時に考える必要がない。
3. **デフォルトでは永続化しない。** stateはメモリに置く。永続化はプロトタイプが確認する対象であり、依存するものではない。問いがデータベースを明示的に扱う場合は、スクラッチDBまたは「PROTOTYPE, wipe me」と明示したローカルファイルを使う。
4. **磨き込みを省く。** テスト、プロトタイプを**実行可能**にする以上のエラーハンドリング、抽象化は加えない。目的は素早く学ぶことである。
5. **stateを表に出す。** actionの後（ロジック）またはバリエーションの切り替えごと（UI）に、関係するstate全体を表示または描画し、何が変わったかをユーザーが見られるようにする。
6. **完成したら記録する。** 検証済みの決定を本物のコードに取り込み、スキルの説明どおりにプロトタイプ自体を**主要な情報源**として記録する。捨てブランチにコミットし、mainの外に置く。実装課題には、そのブランチへの参照条件付きの案内（context pointer）を残す。答え（結論と解決した問い）も課題またはコミットに記録する。mainブランチに残すのは検証済みの決定だけである。
