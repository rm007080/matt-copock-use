# ロジックのプロトタイプ

誰でもボタンをクリックして状態モデルを動かせる、単一の自己完結型HTMLファイル（**共有可能なデモ**）を作る。これは**ビジネスロジック（business logic）**、状態遷移、データの形に関する問いに使う。紙の上では妥当に見えるが、実際のケースに通すと初めて違和感がわかるような問いである。

インストールするものがない1ファイルなので、デザイナー、PM、ドメイン専門家などの開発者でない人に渡し、自分でモデルを体感してもらえる。だからコードの言葉ではなく、相手の言葉で話す。

## この形が適する場合

- 「Xの後にYが起きるエッジケースを、このステートマシン（state machine）は処理できるのか分からない」
- 「このデータモデルで、本当に…というケースを表現できるのか」
- 「実装する前に、APIがどう見えるべきかを体感したい」
- 誰かが**ボタンを押して状態の変化を見る**ことを望む場合

問いが「これはどう見えるべきか」なら、ここは間違った分岐である。[UI.md](UI.md) を使う。

## プロセス

### 1. 問いを明示する

コードを書く前に、どの状態モデルを、どの問いのためにプロトタイプ化するかを書き出す。デモの先頭で、見える導入文として置く（コメントだけにしない）。間違った問いに答えるロジックのプロトタイプは完全な無駄なので、問いを明示しておく。ユーザーが今見ているか、AFK（離席中）に後で戻るかに関係なく、後から確認できるようにする。

### 2. ロジックを移植可能なmodule（モジュール）に分離する

問いに答える実際のロジックを、後で本物のコードベースから取り出して移せる、小さく純粋なmoduleとして単一の `<script>` ブロックに置く。ページの周りは捨てるものだが、このmoduleはそうではない。

正しい形は問いによって変わる。

- **純粋なreducer（リデューサー）**: `(state, action) => state`。actionが離散的なイベントで、stateが単一の値のときに適する。
- **ステートマシン**: 明示的なstateと遷移。「今この時点で、どのactionが合法なのか」自体が問いの一部である場合に適する。
- **純粋関数の小さな集合**: 単純なデータ型に対して使う。暗黙の現在stateがなく、変換だけがある場合に適する。
- **明確なメソッド表面を持つクラスまたはmodule**: ロジックが継続する内部stateを本当に所有する場合に使う。

ページに配線しやすい形ではなく、問われている問いに最も合う形を選ぶ。純粋に保つ。DOMも `document` も使わず、ボタンハンドラーが内部に入り込まないようにする。ページがmoduleを呼び、逆方向には何も流れない。これが、プロトタイプを寿命の後まで役立たせる。問いに答えたら、検証済みのreducer / machine / function setをそのまま本物のmoduleへ移せる。

### 3. 共有可能なHTMLファイルを作る

1ファイル、素のHTML/CSS/JSにする。フレームワーク、バンドラー、サーバーを使わず、ダブルクリックで開け、メールで回しても動くようにすべてインラインにする。開くだけで誰でも実行できるようにする。

開発者でない人向けに書く。すべてのラベルはコードではなく**ドメイン言語**にする。ボタンとstateはreducerではなくビジネスの言葉で読めるようにする。起きていることを平易な言葉で説明する。

上から下への明確な階層で配置する。

1. **タイトルと1行の説明**: このデモで何を試せるか（ステップ1の問い）を示す。
2. **現在のstate**: 関係するstate全体を、読みやすいパネルとして描画する（生のJSONダンプではなく、ラベル付きフィールド）。クリックのたびに再描画し、変化を見えるようにする。開発者でない人が追いやすくなるなら、直前に何が変わったかを示す。
3. **自由操作ボタン**: actionごとに1つのボタンを常に使えるようにし、誰でもモデルを好きな順番で試せるようにする。クリックするたびにactionをdispatch（ディスパッチ）し、stateを再描画する。
4. **案内付きウォークスルー**: タブごとに1つの**シナリオ**を置く。各タブにはシナリオの短い平易な説明（設定する状況と注目点）を置き、その下にそのシナリオで押す順序付きの**ボタン**を置く。各ステップは実際のボタンにする。クリックするとactionを実行し、次のステップへ進む。ウォークスルーの開始時には既知の初期stateへリセットし、毎回同じようにシナリオを実行できるようにする。

紙の上では考えにくい気まずいケースを示すシナリオを選ぶ。正常系、難しいエッジケース、違法であるべき操作の試行などである。

美しく、しかし抑制された見た目にする。明瞭なタイポグラフィ、十分な余白、1つのアクセント色。アニメーションや小細工は使わない。stateとボタンの邪魔になるものを置かない。

### 4. 引き渡す

ファイルを送るか、開いて見せる。相手は都合のよいときにウォークスルーと自由操作を試す。面白い瞬間は「待って、それはできるべきではない」や「ええと、Xは違うと思っていた」と言うときである。それがアイデアのバグであり、そこが目的そのものである。新しいactionやシナリオが必要なら追加する。プロトタイプは進化する。

### 5. 答えとプロトタイプを記録する

プロトタイプが問いに答えたら、答えを記録し、[SKILL](SKILL.md) が説明する方法でプロトタイプも記録する。ロジック固有の対応は次のとおり。検証済みのreducer / machine / function setを本物のmoduleに移し、決定を吸収する。HTMLシェルは、プロトタイプを主要な情報源として保持する捨てブランチに一緒に置く。自己完結型の1ファイルなので、そこで簡単に再実行できる。

## アンチパターン

- **テストを追加しない。** テストが必要なプロトタイプは、もうプロトタイプではない。
- **本物のデータベースへ接続しない。** 問いが永続化を特に扱う場合を除き、メモリ内のstateを使う。
- **一般化しない。** 「将来Xをサポートしたくなったら」は考えない。プロトタイプは1つの問いに答える。
- **ロジックとページを一緒にしない。** 純粋なmoduleがDOM、`document`、ボタンハンドラーを参照するなら、もう移植できない。ページは純粋なmoduleの薄いシェルにする。
- **フレームワーク、バンドラー、サーバーに手を伸ばさない。** 受け取った人がダブルクリックする1ファイルにする。Reactアプリや開発サーバーでは「共有可能」という目的が損なわれる。
- **HTMLシェルをプロダクションに出荷しない。** ページは手でクリックすることに最適化されている。残す価値があるのは、その背後のロジックmoduleである。
