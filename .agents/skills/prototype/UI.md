# UIのプロトタイプ

1つのルート上に、根本的に異なる**UIバリエーション（UI variations）**を複数生成し、画面下部に浮かぶバーから切り替えられるようにする。ユーザーはブラウザーでバリエーションを切り替え、1つを選ぶ（またはそれぞれから一部を取る）。残りは捨てる。

問いがロジック / stateに関するもので、見た目に関するものでないなら、ここは間違った分岐である。[LOGIC.md](LOGIC.md) を使う。

## この形が適する場合

- 「このページはどう見えるべきか」
- 「決める前に、このダッシュボードのいくつかの選択肢を見たい」
- 「設定画面の別のレイアウトを試して」
- 3つの曖昧なモックアップを頭の中で比較するために、丸1日使ってしまいそうなとき

## 2つの下位形: 下位形Aを強く優先する

UIプロトタイプは、アプリの残りの部分、本物のヘッダー、本物のサイドバー、本物のデータ、本物の密度に**接している**と、はるかに判断しやすい。単独の捨てルートは真空状態であり、すべてのバリエーションが孤立して見ればよく見える。バリエーションを置ける妥当な既存ページがあるなら、常に下位形Aをデフォルトにする。近くに置ける場所が本当にないときだけ下位形Bを使う。

### 下位形A: 既存ページへの調整（推奨）

ルート（route）はすでに存在する。バリエーションは `?variant=` URL検索パラメーターで制御し、**同じルート上**に描画する。既存のデータ取得、パラメーター、認証はすべて維持する。切り替えるのは描画だけである。これをデフォルトにし、特別な理由がない限り選ぶ。

プロトタイプ対象がまだページを持たないが、自然にはページの中に置かれるもの（ダッシュボードの新しいセクション、設定画面の新しいカード、既存フローの新しいステップ）なら、それでも下位形Aである。ホストページの中にバリエーションをマウントする。

### 下位形B: 新しいページ（最後の手段）

プロトタイプ対象が置ける既存ページを本当に持たない場合だけ使う（まったく新しいトップレベルの画面や、どこにも自然に埋め込めないフローなど）。プロジェクトが既に使っているルーティング規約に従って、**捨てルート**を作る。プロトタイプだと明らかに分かる名前にする（例: パスまたはファイル名に `prototype` を含める）。同じ `?variant=` パターンを使う。

下位形Bを選ぶ前に、妥当性を確認する。本当に埋め込める既存ページがないのか。空のルートは、データがあるページなら露呈する設計上の問題を隠す。

どちらの下位形でも、画面下部に浮かぶバーは同じである。

## プロセス

### 1. 問いを示し、Nを選ぶ

デフォルトは**3バリエーション**とする。5を超えると根本的な違いではなくノイズになり始めるため、上限を5とする。

プロトタイプの場所またはファイル先頭のコメントに、計画を1行で書く。

> 「既存の `/settings` ルート上で、`?variant=` により切り替えられる設定ページの3つのバリエーション。」

ユーザーが反論するためにいる場合でも、いない場合でも機能する。

### 2. 根本的に異なるバリエーションを生成する

各バリエーションを草案にする。それぞれに次を守らせる。

- ページの目的とアクセスできるデータ
- プロジェクトのcomponentライブラリ / スタイリングシステム（TailwindCSS、shadcn、MUI、素のCSSなど）
- `VariantA`、`VariantB`、`VariantC` のような明確なexport済みcomponent名

バリエーションは**構造的に異なる**ものにする。レイアウト、情報階層、主要な操作手段を変える。色だけが違うカードグリッドや、少し調整したカードグリッドを3つ作るのはUIプロトタイプではなく壁紙である。2つの草案が似すぎたら、「カードグリッドを使わない」と明示して1つをやり直す。

### 3. つなぎ合わせる

ルートに単一の切り替えcomponentを作る。

```tsx
// 疑似コード。プロジェクトのフレームワークに合わせて調整する
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

下位形A（既存ページ）では、切り替えの上にある既存のデータ取得をすべて維持する。バリエーションごとに描画されるサブツリーだけを変える。

下位形B（新しいページ）では、`/prototype/<name>` の捨てルートに同じ切り替えをマウントする。

### 4. 画面下部に浮かぶ切り替えを作る

画面の下中央に固定する小さなバーを置き、次の3つを含める。

- **左矢印**: 前のバリエーションへ進む（末尾から先頭へ循環する）。
- **バリエーションのラベル**: 現在のバリエーションキーと、バリエーションが名前をexportしていればその名前も表示する。例: `B (Sidebar layout)`。
- **右矢印**: 次のバリエーションへ進む（末尾から先頭へ循環する）。

振る舞い:

- 矢印をクリックするとURL検索パラメーターを更新する（Nextなら `router.replace`、React Routerなら `navigate` などフレームワークのrouterを使う）。これにより、バリエーションを共有でき、リロードしても維持される。
- キーボードでは `←` と `→` の矢印キーでも切り替える。`<input>`、`<textarea>`、または `[contenteditable]` にフォーカスがあるときは矢印キーを横取りしない。
- ページと視覚的に区別する（高コントラストのピル、控えめな影など）。評価対象のデザインの一部ではないと明らかに分かるようにする。
- プロダクションビルドでは非表示にする。`process.env.NODE_ENV !== 'production'` または同等のチェックでゲートし、プロトタイプのマージミスでバーがユーザーに出荷されないようにする。

切り替えは単一の共有componentに置き、両方の下位形で再利用できるようにする。プロジェクトの共有UIが置かれている場所に配置する。

### 5. 引き渡す

URL（および `?variant=` のキー）を提示する。ユーザーは都合のよいときに切り替える。通常、面白いフィードバックは「BのヘッダーとCのサイドバーがほしい」であり、それが実際に求められているデザインである。

### 6. 答えを記録し、片付ける

バリエーションが決まったら、どのバリエーションかとその理由を記録し、[SKILL](SKILL.md) の説明どおりにプロトタイプも記録する。勝者を本物のコードに取り込み、残りをmainではなく捨てブランチへ移す。

- **下位形A**: 勝者を既存ページに取り込み、mainから負けたバリエーションと切り替えを削除する。
- **下位形B**: 勝者を本物のルートに昇格し、mainから捨てルートと切り替えを削除する。

バリエーションの全体は主要な情報源である。だから捨てずに捨てブランチへ置く。バリエーションcomponentと切り替えをmainに残すとすぐに腐り、次の読者を混乱させる。

## アンチパターン

- **色や文言だけが違うバリエーション。** それは調整であり、プロトタイプではない。本物のバリエーションは構造で意見が分かれる。
- **バリエーション間でコードを共有しすぎる。** 共有の `<Header>` はよい。共有の `<Layout>` は目的を損なう。各バリエーションはレイアウトを自由に捨てられるようにする。
- **バリエーションを本物の変更に接続する。** 読み取り専用のプロトタイプはよい。変更が必要ならスタブに向ける。問いは「これはどう見えるべきか」であり、「バックエンドは動くか」ではない。
- **プロトタイプを直接プロダクションへ昇格する。** バリエーションのコードは、テストなし・最小限のエラーハンドリングというプロトタイプの制約下で書かれている。取り込むときは適切に書き直す。
