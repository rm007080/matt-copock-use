# Test-Driven Development

TDD（テスト駆動開発）はred → greenのループである。このスキルは、そのループで残す価値のあるテストを作るための基準となる。良いテストとは何か、テストをどこに置くか、アンチパターン、ループの規則を扱う。すべてのセクションはすべてのサイクルに適用する。ループの後ではなく、前と途中で参照する。

コードベースを探索するときは、プロジェクトのドメイン言語とテスト名を合わせるため、`CONTEXT.md`（存在する場合）を読む。触れる領域のADR（アーキテクチャ決定記録）にも従う。

## 良いテストとは

テストはimplementation（実装）の詳細ではなく、公開interface（インターフェース）を通して振る舞いを検証する。コードが完全に変わっても、テストは変わらないべきである。良いテストは仕様のように読める。「ユーザーが有効なカートでチェックアウトできる」は、存在する能力を正確に伝える。内部構造を気にしないため、リファクタリングにも耐える。

[tests.md](tests.md) に例があり、[mocking.md](mocking.md) にモックの指針がある。

## テストを置くseam（継ぎ目）

確認が必要な場合は、調査で分かることと回答済みの内容を除き、原則1問につき独立した判断または事実確認を1点だけ尋ねる。現在の実行モードで使える質問ツールを使い、なければ文章で尋ねる。判断には推奨案と短い理由を添え、事実確認には必須としない。回答を待って次の確認を選び直す。ユーザーの明示依頼時だけ、その範囲で互いの回答に依存しない質問をまとめる。

判断に「分からない」と言われたら推奨案を採用するか確認する。不明な事実は未確定として扱う。終了を求められたら質問を止め、決定事項・未決事項・次のステップ候補を短くまとめる。

**Seam**はテストする公開境界である。内部に入り込まずに振る舞いを観測するinterfaceの場所である。テストはseamに置き、内部に対しては決して置かない。

**事前に合意したseamだけをテストする。** テストを書く前に、テスト対象のseamを書き出し、推奨する対象と理由を示す。未合意の判断を1つずつ確認し、回答を待つ。確認されていないseamにテストを書かない。すべてをテストすることはできない。先にseamに合意することで、テストの努力を重要な経路と複雑なロジックに向けられる。すべてのエッジケースに向ける必要はない。

まず公開interfaceをコードから調べ、そのうちどのseamをテストするかをユーザーと判断する。

そのinterfaceの形自体が問題になっている場合（module（モジュール）の深さ、seamの場所、interfaceが公開すべきもの）、語彙のためにSkillツールで「codebase-design」を呼び出す。それはmodule、interface、depth（深さ）、seam、adapter（アダプター）、leverage（てこ）、locality（局所性）という語の共有ソースであり、実行するセッションではなく、参照する資料である。

## アンチパターン

- **implementationに結合している**: 内部の協力要素をモックする、privateメソッドをテストする、または横道（interfaceを使わずにデータベースを照会するなど）で検証する。兆候は、振る舞いが変わっていないのにリファクタリングでテストが壊れることである。
- **同語反復的である**: アサーションがコードと同じ方法で期待値を再計算する（`expect(add(a, b)).toBe(a + b)`、手で同じように導出したスナップショット、定数が自分自身と等しいことの検証）。そのため、構成によって通り、コードと食い違うことがない。期待値は独立した真実の情報源、つまり既知のリテラル、計算済みの例、仕様から得る。
- **水平分割**: まずすべてのテストを書き、次にすべてのimplementationを書く。一括テストは想像上の振る舞いを検証する。ユーザーに見える振る舞いではなく、物の形をテストするため、テストは実際の変更に反応しなくなり、implementationを理解する前にテスト構造を確定してしまう。代わりに **vertical slices（縦断的な作業単位）** で進める。1つのテスト → 1つのimplementationを繰り返し、各テストを、直前のサイクルで分かったことに応じる **tracer bullet（最小の縦断実装）** にする。

## ループの規則

- **greenの前にred。** まず失敗するテストを書き、それを通すのに必要なコードだけを書く。将来のテストを先回りしたり、推測で機能を追加したりしない。
- **一度に1つのslice。** 1つのseam、1つのテスト、1つの最小implementationを1サイクルにする。
- **リファクタリングはループの一部ではない。** レビュー段階に属する（`code-review` スキルを参照）。red → greenの実装サイクルには含めない。
