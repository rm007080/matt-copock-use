# Domain Modeling

設計しながらプロジェクトのドメインモデルを積極的に構築し、磨き上げる。これは *active（能動的）* な規律である。用語に異議を唱え、エッジケースのシナリオを考え、用語集と決定を具体化した瞬間に書き留める。`CONTEXT.md` を単に読んで語彙を得ることはこのスキルではない。それはどのスキルでもできる1行の習慣である。このスキルは、モデルを変更するときに使う。

## ファイル構成

ほとんどのリポジトリは単一コンテキストを持つ。

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` があるなら、リポジトリは複数のコンテキストを持つ。マップは各コンテキストの場所を指す。

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延作成する。書くものがあるときだけ作る。`CONTEXT.md` がなければ、最初の語が解決されたときに作る。`docs/adr/` がなければ、最初のADRが必要になったときに作る。

## セッション中

### 用語集に照らして問い直す

ユーザーが `CONTEXT.md` にある既存の言葉と矛盾する語を使ったら、すぐに指摘する。「用語集では『cancellation』をXと定義していますが、Yを意味しているようです。どちらですか？」

### 曖昧な言葉を磨く

ユーザーが曖昧な語や意味の重なった語を使ったら、正確な標準語を提案する。「『account』と言っていますが、CustomerとUserのどちらですか。この2つは異なるものです。」

### 具体的なシナリオを話し合う

ドメインの関係を話し合うときは、具体的なシナリオでストレステストする。エッジケースを探り、概念間の境界を正確にするシナリオを考える。

### コードと相互参照する

ユーザーが何かの仕組みを説明したら、コードが一致しているか確認する。矛盾を見つけたら、それを表に出す。「コードはOrder全体をキャンセルしていますが、今は部分キャンセルが可能だと言いました。どちらが正しいですか？」

### CONTEXT.mdをその場で更新する

用語が解決したら、すぐに `CONTEXT.md` を更新する。後でまとめて更新しない。[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) の形式を使う。

`CONTEXT.md` には実装の詳細を一切入れない。仕様、作業用メモ、実装上の決定を保存する場所として扱わない。これは用語集であり、それ以外ではない。

### ADRは控えめに提案する

次の3つがすべて真のときだけADRの作成を提案する。

1. **戻しにくい**: 後から考えを変えるコストが意味のある大きさである
2. **文脈がないと意外である**: 将来の読者が「なぜこの方法にしたのか」と思う
3. **本当のトレードオフの結果である**: 本当の代替案があり、具体的な理由でその1つを選んだ

3つのうち1つでも欠けるなら、ADRを飛ばす。[ADR-FORMAT.md](./ADR-FORMAT.md) の形式を使う。
