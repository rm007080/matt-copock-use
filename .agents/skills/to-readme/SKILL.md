利用者が「何ができるか・自分に役立つか」を判断し、最初の利用を始められる README を作成・更新する。対象プロジェクトの資料を根拠にし、特定の技術や文書構成を前提にしない。

## 手順

1. **対象を特定する。** ユーザーの指定と作業場所から、対象プロジェクトと README を特定する。そのプロジェクトの指示と既存 README を読み、指定された形式・言語・変更範囲を優先する。複数候補から対象を特定できない場合は確認する。
2. **根拠を集める。** 目的・主な用途・利用条件・最初の利用に必要なコード、設定、実行入口、関連資料、対象についての会話の合意を読む。仕様書・用語集・課題管理設定がなくても、存在する資料で進める。別のエージェントスキルの導入や文書の先行作成を前提条件にしない。
3. **重要な不足を確認する。** 調査で分かることは自分で確認する。利用条件・導入・基本利用を左右する不足や矛盾だけを、使える質問ツールで原則1問ずつ尋ねる。ツールがなければ文章で尋ねる。1問は独立した判断または事実確認の1点とし、回答を待って次の確認を選び直す。判断には推奨案と短い理由を添える。回答待ちの内容を推測で補わず、軽微な項目を埋めるためだけに質問を続けない。
4. **新規作成・更新する。** 下記の内容を対象に合わせて構成する。既存 README は有効な説明、人の編集、関連リンクを生かし、依頼に関係する箇所を更新する。繰り返し更新しても同じ項目を重複させない。
5. **確認して報告する。** 保存後に読み戻し、機能や手順の根拠、参照するファイル・リンク先、依頼した範囲との一致を確認する。作成・更新したファイル、確認した内容、残る未検証事項を報告する。

## 内容と根拠

- 基本は、概要、主な用途、前提条件、導入、基本的な使い方、詳しい資料へのリンク。必要な項目を選び、固定の見出しを埋めるために内容を作らない。資料集なら閲覧・利用の案内を中心にするなど、プロジェクトに合う利用開始方法を示す。
- 現在利用できる機能、予定の機能、未確認の動作を区別する。仕様に書かれた目標だけを、実装済みの根拠にしない。導入コマンドや設定値は実際の設定・実行入口・資料と照合し、不明な値や選定理由を捏造しない。
- 詳細な仕様や長い手順は概要とリンクで案内する。既存の導入スクリプトや手順への有効なリンクを保持し、リンク先と説明を確認する。要求・設計の管理先がある場合はその役割を保ち、README の編集だけで元の合意を変更しない。
- コマンドの根拠確認と実行確認を分け、実行していないものを動作確認済みとしない。手順を文書化するためだけに、環境構築・デプロイ・外部送信を実行しない。実行確認が必要な場合は、対象環境の権限と既存の承認範囲に従う。

## 完了と制約

依頼された範囲の説明と利用手順に根拠があり、重要な不足・矛盾が解消し、保存と読み戻しを確認できれば完了とする。実行確認など残る未検証事項は明示する。重要な質問への回答待ちや保存失敗は完了扱いにしない。

Planモードなど書き込めない環境では会話内に案を提示し、未保存と伝える。README の作成・更新を、他文書の一式作成や、コード変更後の自動更新・公開へ広げない。
