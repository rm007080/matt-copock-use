# Ask Matt

すべてのスキルを覚えているわけではないので、尋ねてください。

**フロー（flow）**は、スキルを通る道筋です。ほとんどの道は1つの**メインフロー**に沿い、2つの**導入路（on-ramp）**がそこへ合流します。それ以外は単独で使うか、下で動く語彙の層です。

## メインフロー：アイデアから出荷まで

多くの作業が通るルートです。アイデアがあり、それを構築したいとします。

1. **`/grill-with-docs`** はインタビューでアイデアを具体化します。**作業ディレクトリで作業している**ときは必ずここから始めてください。これは状態を保持し、学んだことを `CONTEXT.md` とADR（アーキテクチャ決定記録）に残します。（作業ディレクトリがない場合は、「単独で使うもの」で扱う **`/grill-me`** を使います。どちらも同じ **`/grilling`** プリミティブを実行しますが、`grill-with-docs` は記録を残します。リポジトリが記録を残せる場所にあるなら、こちらの方が適しています。）
2. **分岐：すべての質問を会話で解決できますか？** 実行可能な答え（状態、ビジネスロジック、実際に見る必要があるUI（ユーザーインターフェース））が必要なら、**`/handoff`** で両方向を橋渡ししてプロトタイプへ寄り道します。（プロトタイプは専用ディレクトリに置くので、まさに **`/handoff`** の用途です。フェーズ境界を参照してください。）
   - **`/handoff`** で外へ渡し、そのファイルに対して新しいセッションを開く。
   - **`/prototype`** で使い捨てコードを使って質問に答える。
   - 学んだことを **`/handoff`** で戻し、元のアイデアのスレッドから参照する。
3. **分岐：複数セッションにまたがる構築ですか？**
   - **Yes** → **`/to-spec`**（スレッドを仕様に変える）、次に **`/to-tickets`** で**最小の縦断実装チケット（tracer-bullet tickets）**へ分割し、それぞれに**ブロッキング関係（blocking edges）**を宣言します。ローカルのトラッカーではチケットごとに `.scratch/<feature>/issues/` の下へ1ファイルを作り、ブロッカーの解決順に手作業で進めます。実際のトラッカーでは関係がネイティブのブロッキングリンクになるため、ブロッカーが完了したチケットは取得できます。チケットごとに **`/implement`** を開始し、各チケットの間でコンテキストを **`/clear`** します。各チケットは自己完結しているので、最後のチケットのコンテキストは捨てられます。
   - **No** → 同じコンテキストウィンドウで、ここから **`/implement`** します。

どちらの場合も、**`/implement`** は内部で **`/tdd`**（1回に1つのレッド・グリーンの縦断的な作業単位（vertical slice））を進めながら各課題を構築し、コミット前に **`/code-review`** を実行して、差分をStandardsとSpecの2軸でレビューして終えます。完全な仕様がなくても具体的な振る舞いをテストファーストで構築したい場合は **`/tdd`** 単独を使い、固定点に対してブランチまたはPRをレビューしたい場合は **`/code-review`** 単独を使います。

### コンテキストの衛生

ステップ1〜3は**1つの途切れないコンテキストウィンドウ**に保ちます（グリル、仕様、チケットが同じ思考の上に積み上がるよう、`/to-tickets` の後までコンパクトやクリアをしないでください）。その後の各 **`/implement`** は、チケットを起点に新しく始めます。

この長さには **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**（スマートゾーン）という上限があります。これは、最先端モデルがなお鋭く推論できるウィンドウ（約15万トークン）です。`/to-tickets` の前にセッションが上限に近づいたら、劣化した状態で押し進めず、最寄りのフェーズ境界で **`/compact`** して続けます（フェーズ境界を参照）。

## 導入路

作業を生み出し、そこからメインフローへ合流する開始状況です。

- **バグや依頼が積み上がっている** → **`/triage`**。課題をトリアージの役割に沿って動かし、後で **`/implement`** が取り上げられるエージェント対応可能な課題を作ります。

  トリアージは**あなたが作成していない**課題だけを対象にします。バグ報告、届いた機能要望、生のまま到着したものが対象です。`/to-tickets` が作ったチケットはすでにエージェント対応可能なので、**トリアージしないでください**。

- **何かが壊れている** → **`/diagnosing-bugs`**。最初の一見では分からないバグ、断続的に発生する不安定さ、既知の正常状態の間に入り込んだリグレッションなど、難しいものに使います。このスキルは、まず**厳密なフィードバックループ**（このバグをすでに失敗させる1つのコマンド）ができるまで理論化を拒み、その後リグレッションテストで修正します。本当の発見が、バグを固定する良い**seam（接合点）**がないことなら、事後分析を **`/improve-codebase-architecture`** に引き継ぎます。

- **巨大で霧のかかった取り組み：1セッションでは大きすぎるグリーンフィールドプロジェクトまたは巨大な機能構築** → **`/wayfinder`**。ここで最も認知的負荷の高いフローです。現在地から**目的地**への道がまだ見えていないとき、課題トラッカー上に**決定チケット**の**共有マップ**を作り、霧が後退して道が明確になるまで一つずつ解決します。生み出すのは**成果物ではなく決定**です。**`/grill-with-docs`** が1セッションで保持できるアイデアを具体化するのに対し、wayfinderは保持できないアイデアのためにあり、遅く密度も高いので、まさにその場合にだけ使い、範囲が明確な機能には使いません。

  マップが明確になったら、**構築せずに引き継ぎます**。**`/to-spec`** でメインフローに合流し、マップのリンクされた決定を構築可能な計画へまとめ、通常どおり `/to-tickets`、`/implement` と続けます。マップから直接 `/implement` へループすると、この統合を飛ばしてリンクされた詳細を捨てるため、取り組みが本当に小さいと分かった場合だけ直接 `/implement` へ進みます。

## コードベースの健全性

機能作業ではなく、保守作業です。

- **`/improve-codebase-architecture`** は、エージェントが操作しやすいコードベースを保つため、余裕があるときに実行します。**深める機会（deepening opportunities）**を見つけ、その1つを選ぶと、`/grill-with-docs` からメインフローへ持ち込める**アイデア**が生まれます。これは候補を見つける調査であり、下記の **`/codebase-design`** は選んだ候補を設計する作業台です。

## 下層の語彙

他のスキルの**下で**動く、モデル呼び出し用の参照が2つあります。それぞれの語彙の唯一の情報源です。問題が**プロセスではなく言葉**にあるときは直接参照し、上のスキルから読み込ませることもできます。

- **`/domain-modeling`**：プロジェクトの*ドメイン*言語を研ぎ澄まします。曖昧な用語に問いを投げ、複数の仕事をしている過負荷な単語（3つの仕事をする「account」など）を解決し、後戻りしにくい決定をADRとして記録します。これは `/grill-with-docs` が `CONTEXT.md` を整理された用語集に保つために進める実践です。
- **`/codebase-design`** は、module（モジュール）の**形**を設計するための **deep module（深いモジュール）**の語彙です。そこには interface（インターフェース）、depth（深さ）、seam（接合点）、adapter（アダプター）、leverage（てこ）、locality（局所性）が含まれます。つまり、clean seamにある小さな interface の背後に多くの振る舞いを置く考え方です。`/tdd` と `/improve-codebase-architecture` はどちらもこの語彙を使います。

## フェーズ境界

**フェーズ（phase）**はセッション内の作業のまとまりです。グリル、implementation（実装）、QA（品質保証）などが該当します。2つのフェーズの**境界**では5つの選択肢があり、このマップ全体で最も曖昧な判断になります。

- **Continue**：その場に留まります。コストも損失もありません。
- **`/clear`**：次に必要なものがここにないとき、ウィンドウを空にします。
- **`/handoff`**：持ち運べるMarkdownファイルを書きます。**新しいハーネス（harness）、新しいディレクトリ、同僚**、またはフェーズ途中での横道の作業の分岐に限って使います。得られるのは可搬性です。
- **Subagent**：範囲を絞った作業を独自のウィンドウに送り、報告を受けます。
- **`/compact`**：このコンテキストを圧縮し、そこから新しいセッションを開始します。ツリーの下端にある**デフォルト**で、最初に選ぶものではありません。

順序付けられたツリー（5つの質問、各分岐の理由、一次情報源のコストによって、他の選択肢に進む前にまず **Continue** で済むかを検討すべき理由）については [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) を読んでください。フェーズの境界**で**判断し、フェーズ途中では続行するか、残りをサブエージェントに分割します。

## 単独で使うもの

メインフローから完全に外れています。

- **`/grill-me`**：`/grill-with-docs` と同じ容赦ないインタビューですが、**ステートレス**です。ローカルに何も保存せず、`CONTEXT.md` も作りません。**作業ディレクトリで作業していない**とき（計画、設計、文章を磨いているときなど、リポジトリがない場合）に使います。作業ディレクトリにいるなら `/grill-with-docs` を使います。同じインタビューを実行して記録も残すので、こちらの方が適しています。
- **`/grilling`**：インタビューそのもののプリミティブです。**着手可能な項目（frontier）**から原則1問ずつ尋ね、回答を待つラウンドを重ねます。まとめて聞くのはユーザーが明示的に求めた範囲だけです。事実はエージェントの仕事で、決定はあなたの仕事です。`/grill-me` と `/grill-with-docs` が名前付きの入口で、`/triage`、`/wayfinder`、`/improve-codebase-architecture` は内部でこれを実行します。ラッパーなしのインタビューが必要なときだけ直接使います。
- **`/resolving-merge-conflicts`**：進行中のマージまたはリベースの競合を、各側の一次情報源から意図をたどって、行を選ぶのではなくハンクごとに解決し、その操作を終えます。`--abort` は決して実行しません。すべてのフローから外れた単独スキルなので、すでに競合中のときに使います。
- **`/prototype`**：1つの設計上の質問に答える、小さく使い捨てのプログラムです。状態モデルが適切か、UIをどう見せるべきかを確認します。使い捨てという制約はコードの書き方に対するもので、破棄を約束するものではありません。答えは本番コードに取り込み、プロトタイプ自体も `prototype/<name>` ブランチ上の**一次情報源**として保持し、実装課題から指し示します。メインフローのステップ2にある寄り道ですが、紙の上で決めにくい設計質問にはいつでも使えます。
- **`/research`**：読み取り作業を**バックグラウンドエージェント**に委任します。エージェントは**一次情報源**に基づいて質問を調査し、引用付きMarkdownファイルをリポジトリに残します。調査中も作業を続けられます。そのファイルは、調査が思考を置き換えるのではなく、メインフローの `/grill-with-docs` に持ち込むためのものです。
- **`/to-questionnaire`**：あなたの頭やコードベースではなく**誰か別の人**の中にある情報が作業を止めているときに使い、その人が記入する質問票を書きます。`/grill-me` の逆で、対象についてあなたをインタビューするのではなく、**送信**（誰に送り、何を返してもらうか）をインタビューし、空白に向けて質問します。戻ってきたものは `/grill-with-docs` または `/to-spec` の材料になります。
- **`/wizard`**：**人間にしかできない**手順、つまりインフラのプロビジョニング、認証情報やCIシークレットの設定、不慣れな第三者ダッシュボードでのクリック、1回限りの移行や切り替えに使います。対話式のbashスクリプトを生成し、各URLを開いて値を取得し、`.env` とGitHubシークレットへ書き込みます。そのため、毎回エージェントに説明し直す手順ではなくなります。モデル呼び出し用なので、あなたにしか越えられない壁に当たった瞬間にエージェントはこれを使います。エージェント自身ができるならそうするべきで、これは人間が本当に関与する場所のためのものです。
- **`/wait-what`**：届かなかったメッセージを修正するものです。他のスキルの途中でも使えます。エージェントは不足していたコンテキストを使い、`CONTEXT.md` の語彙で、分かりやすい英語に言い換えて提示します。これは後から効く対処です。前もって `/grill-with-docs` を使うのが予防策で、早い段階で共有語彙を合意しておけば、そもそも専門語が現れにくくなります。
- **`/teach`**：現在のディレクトリを状態を持つワークスペースとして使い、複数セッションにわたって概念を学びます。
- **`/writing-for-agents`**：エージェントが読む文書、つまりスキル、AGENTS.md、参照先ドキュメントを書くためのリファレンスです。

## 前提条件

**`/setup-matt-pocock-skills`**：最初のエンジニアリングフローの前に実行し、他のスキルが前提とする課題トラッカー、トリアージラベル、ドキュメント構成を設定します。カスタムの課題トラッカーも使えます。
