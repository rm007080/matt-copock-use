# バグの診断

難しいバグに取り組むための規律。明確な理由がある場合に限り、フェーズを省略する。

コードベースを調査するときは、`CONTEXT.md` があれば読んで、関係するmodule（モジュール）の明確な全体像をつかみ、対象領域の設計判断記録（ADR）を確認する。

## 対話での確認

確認が必要な場合は、調査で分かることと回答済みの内容を除き、原則1問につき独立した判断または事実確認を1点だけ尋ねる。現在の実行モードで使える質問ツールを使い、なければ文章で尋ねる。判断には推奨案と短い理由を添え、事実確認には必須としない。回答を待って次の確認を選び直す。ユーザーの明示依頼時だけ、その範囲で互いの回答に依存しない質問をまとめる。

判断に「分からない」と言われたら推奨案を採用するか確認する。不明な事実は未確定として扱う。終了を求められたら質問を止め、決定事項・未決事項・次のステップ候補を短くまとめる。

## 機密情報を伏せる

このスキルでは、コマンド、出力、取得した成果物を提示する。**まずすべての機密情報を伏せる**。その箇所を `<REDACTED>` に置き換える。環境変数を使って反復手順を組み、認証情報を提示内容に含めず環境内に保つ。取得した成果物には認証ヘッダーが含まれるため、手掛かりになる行だけを引用する。

機密情報を伏せた出力ではバグを診断できない場合は、その旨を伝えてユーザーに相談する。

## フェーズ1：フィードバックループを作る

**これこそが、このスキルの核心である。** バグについて**速く、決定的で、無駄の少ない（tight）**成否の判定手段があれば（_この_バグで失敗を示すもの）、原因を見つけられる。二分探索、仮説検証、計測用の処理追加は、すべてこの判定手段を利用するだけである。それがなければ、いくらコードを眺めても解決できない。

ここには、ほかの段階よりも多くの労力を注ぐ。**積極的に取り組む。創意工夫する。諦めない。**

### 反復手順を作る方法：おおむねこの順で検討する

1. バグに到達できるseam（振る舞いを差し替えられる接点）での**失敗するテスト**。単体、結合、端から端までのテスト（e2e）のいずれでもよい。
2. 実行中の開発サーバーに対する**Curl／HTTPスクリプト**。
3. 決まった入力データ（fixture）を使った**コマンドライン（CLI）の実行**。標準出力を、正しいことが分かっている保存結果と比較する。
4. 画面を表示せずにブラウザーを操作する**ヘッドレスブラウザースクリプト（headless browser script）**（Playwright／Puppeteer）。ユーザーインターフェース（UI）を操作し、ページの構造（DOM）、コンソール、通信に対して検証する。
5. **取得した実行記録（trace）を再生する。** 実際のネットワークリクエスト／送信データ／イベントログをディスクに保存し、切り離したコード経路で再生する。
6. **使い捨ての検証用プログラム（harness）。** システムの最小部分（1つのサービス、模擬の依存先）を起動し、1回の関数呼び出しでバグのコード経路を実行する。
7. **性質検証／ランダム入力による反復（property / fuzz loop）。** バグが「ときどき出力が間違う」ものであれば、ランダムな入力を1000件実行して、失敗の現れ方を探す。
8. **二分探索用の検証プログラム。** 既知の2つの状態（コミット、データセット、バージョン）の間でバグが発生したなら、「状態Xで起動、確認、繰り返し」を自動化し、`git bisect run` で実行できるようにする。
9. **差分比較による反復。** 同じ入力を旧バージョンと新バージョン（または2つの設定）に与え、出力を比較する。
10. **人が参加する（HITL）bashスクリプト。** 最後の手段。人によるクリックが不可欠なら、`scripts/hitl-loop.template.sh` で_その人_の操作を導き、反復手順の構造を保つ。取得した出力を自分へのフィードバックにする。

適切なフィードバックループを作れば、バグの修正は9割終わっている。

### 反復手順を引き締める

反復手順を1つの製品として扱う。_何らかの_手順ができたら、**引き締める**。

- もっと速くできるか。（準備結果を再利用する、無関係な初期化を省く、テスト範囲を狭める。）
- 判定をもっと明確にできるか。（「クラッシュしなかった」ではなく、具体的な症状を検証する。）
- 結果をもっと一定にできるか。（時刻を固定する、乱数の初期値を固定する、ファイルシステムを隔離する、通信を固定する。）

30秒かかり結果が不安定な手順は、何もないより少しましなだけである。2秒で結果が一定の手順なら引き締まっており、デバッグの強力な武器になる。

### 結果が一定しないバグ

目標は完全に安定した再現ではなく、**再現率を高めること**である。引き金となる操作を100回繰り返し、並列化し、負荷を加え、タイミングの幅を狭め、待ち時間を挿入する。発生率50%ならデバッグできるが、1%ではできない。デバッグできる水準まで発生率を上げ続ける。

### どうしても反復手順を作れない場合

作業を止め、できないことを明示する。試した内容を列挙する。ユーザーに、(a) 再現する環境へのアクセス、(b) 機密情報を伏せた取得物（HTTP通信記録のHARファイル、ログの書き出し、メモリーの記録であるコアダンプ、時刻付き画面録画）、(c) 本番環境に一時的な計測処理を追加する許可、のいずれかを求める。反復手順がないまま仮説の検討に進んではならない。

### 完了条件：引き締まっていて、失敗を検出できる反復手順

フェーズ1の完了には、反復手順が**引き締まっていること**と**失敗を検出できること（red-capable）**が必要である。**すでに1回以上実行した**（呼び出しと機密情報を伏せた出力を示す）**1つのコマンド**（スクリプトのパス、テストの呼び出し、curl）を挙げられ、次を満たすこと。

- [ ] **失敗を検出できる**：実際のバグのコード経路を通り、**ユーザーが報告した症状そのもの**を検証する。このバグがあると失敗し、修正すると成功する。「エラーなく実行できる」だけでは足りず、_この特定のバグを検出_できなければならない。
- [ ] **結果が一定**：毎回同じ判定になる（不安定なバグは、前述のとおり高い再現率で安定している）。
- [ ] **速い**：分単位ではなく、秒単位である。
- [ ] **エージェントが実行できる**：人が付き添わずに実行できる。人が参加する場合は `scripts/hitl-loop.template.sh` のみを使う。

このコマンドが存在する前に、理論を組み立てるためにコードを読んでいると気付いたら、**止める。いきなり仮説に飛び付くことこそ、このスキルが防ぐ失敗である。** 失敗を検出できるコマンドがなければ、フェーズ2へ進まない。

## フェーズ2：再現と最小化

反復手順を実行する。バグが現れて失敗になることを確認する。

次を確認する。

- [ ] **ユーザー**が説明した失敗の現れ方を再現しており、たまたま近くで起こる別の失敗ではない。違うバグなら、修正も間違う。
- [ ] 複数回の実行で失敗を再現できる（結果が一定しないバグなら、デバッグに十分な率で再現できる）。
- [ ] 正確な症状（エラーメッセージ、誤った出力、遅延時間）を記録してあり、後のフェーズで修正が実際にその症状を解消したか検証できる。

### 最小化

失敗したら、再現手順を**失敗し続ける最小のシナリオ**に縮める。入力、呼び出し元、設定、データ、手順を**1つずつ**減らし、減らすたびに反復手順を実行する。失敗の成立に不可欠なものだけを残す。

この作業の理由：最小の再現手順にすると、フェーズ3で考慮すべき仮説が減り（疑う要素が少なくなる）、フェーズ5では明確な再発防止テストになる。

**残った要素がすべて不可欠**になったら完了する。どれか1つを取り除くだけで、反復手順が成功に変わる状態である。

再現**と**最小化が完了するまで、次に進まない。

## フェーズ3：仮説を立てる

どれかを検証する前に、**優先順位を付けた3〜5個の仮説**を出す。仮説を1つだけ立てると、最初にもっともらしく見えた考えに固執する。

各仮説は、**反証可能**でなければならない。その仮説から何が予測されるかを述べる。

> 形式：「<X> が原因なら、<changing Y> によりバグが消える／<changing Z> により悪化する。」

予測を述べられない仮説は、ただの感覚である。捨てるか、明確にする。

**検証前に、優先順位付きの一覧と順位の理由をユーザーに示す。** ユーザーは、すぐに順位を変えるような業務知識（「3番については、変更をデプロイしたばかり」）や、すでに除外した仮説を知っていることが多い。一覧の共有自体は判断の依頼とせず、自分が付けた順位で進める。ユーザーの判断が必要な論点が生じた場合は、その1点を尋ね、回答に依存する検証は待つ。

## フェーズ4：観測用の処理を追加する

各観測手段を、フェーズ3の具体的な予測に対応付ける。**一度に変える変数は1つにする。**

ツールの優先順位：

1. 環境が対応していれば、**デバッガー／対話実行環境（REPL）での調査**。1つのブレークポイントは10件のログに勝る。
2. 仮説を見分けられる境界に置く、**対象を絞ったログ**。
3. 「すべてログに出してgrepする」は絶対に行わない。

**すべてのデバッグログに**、`[DEBUG-a4f2]` のような一意の接頭辞を付ける。最後の後片付けを1回のgrepで済ませられる。目印のないログは残り、目印のあるログは消せる。

**性能問題の場合。** 性能の悪化に対しては、通常ログは適切でない。代わりに、基準となる測定（時間計測用のプログラム、`performance.now()`、プロファイラー、クエリの実行計画）を確立し、その後に二分探索する。先に測定し、後で修正する。

## フェーズ5：修正と再発防止テスト

**修正前に**再発防止テストを書く。ただし、**適切なseam**が存在する場合に限る。

適切なseamとは、呼び出し箇所で発生する**実際のバグのパターン**をテストできる場所である。利用できるseamがshallow（浅い）すぎる場合（複数の呼び出し元が必要なバグに対する単一呼び出し元のテストや、引き金となった連鎖を再現できない単体テスト）、そこで再発防止テストをしても、誤った安心感を生む。

**適切なseamがなければ、それ自体が発見事項である。** 記録する。コードベースの構造が、バグの再発を確実に防ぐ妨げになっている。次のフェーズに向けて、この点を明示する。

適切なseamが存在する場合：

1. 最小化した再現手順を、そのseamで失敗するテストにする。
2. 失敗することを確認する。
3. 修正を適用する。
4. 成功することを確認する。
5. 元の（最小化していない）シナリオに対して、フェーズ1のフィードバックループを再実行する。

## フェーズ6：後片付け

完了を宣言する前に、次を満たすこと。

- [ ] 元の再現手順でバグが再現しない（フェーズ1の反復手順を再実行する）
- [ ] 再発防止テストが成功する（またはseamがないことが記録されている）
- [ ] `[DEBUG-...]` の観測処理がすべて削除されている（接頭辞を `grep` する）
- [ ] 使い捨ての試作が削除されている（または、デバッグ用と明示した場所へ移されている）
- [ ] 正しかった仮説をコミット／変更提案であるプルリクエスト（PR）のメッセージに記載し、次にデバッグする人が学べるようにしている
