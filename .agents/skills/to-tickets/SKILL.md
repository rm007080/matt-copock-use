# チケットへの分割

計画、仕様書（spec）、または会話を、**チケット（ticket）**の集合に分割する。最小の縦断実装を単位とした縦断的な作業単位（vertical slice）とし、それぞれの**着手を妨げる**チケットを明示する。

課題管理先（issue tracker）と、課題の扱いを分類するトリアージラベル（triage label）の用語は、提供されているはずである。提供されていない場合は、`/setup-matt-pocock-skills` を実行するようユーザーに伝える。

## 手順

### 1. 背景情報を集める

会話内にすでにある情報を基に進める。ユーザーが参照先（仕様書のパス、課題番号、URL）を引数として渡した場合は、取得して本文とコメントをすべて読む。

全体仕様が入力でも、今回チケットにする対象範囲と対象外を特定する。仕様書・計画は任意であり、会話から直接分割してよい。計画は自動生成しない。Wayfinder由来なら、関連する確定した決定票を読み、未決を合意として扱わない。

`docs/agents/issue-tracker.md` の作業フォルダー特定・採番規則と `docs/agents/domain.md` を読む。既存の計画・チケットがあれば同じ作業フォルダーを再利用する。作業が複数候補なら確認する。ローカル作業資料の作成は公開段階まで保留する。

対象範囲の受け入れ条件を左右する未決・矛盾・未同期があれば、計画の有無にかかわらず**フォルダー・チケットの作成、更新、公開前に停止**し、未決内容を会話で返す。仮の `needs-info` チケットも作らない。全体仕様の無関係な未決は停止理由にしない。

### 2. コードベースを調査する（任意）

まだ調査していなければ、コードベースを調べて現在の状態を把握する。チケットのタイトルと説明にはプロジェクトのドメイン用語集の語彙を使い、対象領域の設計判断記録（ADR）に従う。

実装を容易にするため、先にコードを整理する機会を探す。「変更を簡単にしてから、その簡単になった変更を行う。」

### 3. 縦断的な作業単位の案を作る

作業を**最小の縦断実装**のチケットに分割する。

<vertical-slice-rules>

- 各作業単位は、すべての層（データ構造のschema、プログラム間の接続口であるAPI、利用画面のUI、テスト）を通る、狭くても完全な経路を含む。1つの層だけを横に切り出さず、縦に貫く
- 完了した作業単位は、それだけで実演または検証できる
- 各作業単位は、新しい1回分の会話で扱える情報量（context window）に収まる大きさにする
- 事前のコード整理が必要なら、最初に行う

</vertical-slice-rules>

各チケットに、**着手を妨げる依存関係（blocking edges）**を設定する。着手前に完了している必要がある、ほかのチケットである。依存先がないチケットは、すぐに着手できる。

**広範囲のリファクタリングは、縦断的な分割の例外である。** **広範囲のリファクタリング（wide refactor）**とは、列名の変更や共有する名前付き要素の型変更など、影響範囲がコードベース全体へ広がる1つの機械的変更である。1回の編集で数千の呼び出し箇所が同時に壊れ、どの縦断的な作業単位も単独では検証に通る状態で反映できない。無理に最小の縦断実装にせず、**拡張してから縮約する（expand–contract）**順序で進める。まず拡張する。既存のものを壊さないよう、旧形式の隣に新形式を追加する。次に、呼び出し箇所を影響範囲に応じたまとまり（パッケージごと、ディレクトリごと）で移行する。各まとまりを、拡張の完了に依存する独立したチケットにする。旧形式が残っているため、まとまりの移行ごとに継続的インテグレーション（CI）の検査が成功する状態を保つ。最後に縮約する。すべての移行チケットの完了に依存するチケットで、呼び出し元がなくなった旧形式を削除する。まとまり単位でも単独で検証に通る状態を維持できない場合は、この順序を維持しながら共通の統合ブランチを使い、すべてのまとまりを最後の統合・検証チケットの依存先とする。検証の成功を保証するのは、その最後のチケットだけとする。

### 4. ユーザーに確認する

提案する分割を番号付きの一覧で示す。各チケットについて、次を示す。

- **タイトル**：内容を表す短い名前
- **Blocked by**：先に完了すべきほかのチケットがあれば、そのチケット
- **実現すること**：このチケットによって動くようになる、端から端までの振る舞い

次の観点から未解決の判断を選び、原則1問ずつ、推奨案と短い理由を添えて尋ねる。観点の一覧を、そのまま同時に質問しない。

- 粒度：作業単位が粗すぎる、または細かすぎる箇所。
- 依存関係：実際に着手の前提となるチケットとの対応。
- 構成：統合または再分割を検討すべき箇所。

1問には独立した判断を1つだけ含める。現在の実行モードで使える質問ツールを使い、なければ文章で尋ねる。回答を待ち、分割案と次に確認する判断を見直す。調査で分かることや、先回りした回答も含めて回答済みのことは聞き直さない。ユーザーの明示依頼時だけ、指定範囲で互いの回答に依存しない質問をまとめる。

事実確認が必要な場合は1点だけ尋ね、推奨案を必須とせず、不明な事実を推測で埋めない。判断に「分からない」と言われたら推奨案を採用するか確認する。終了を求められたら質問を止め、決定事項・未決事項・次のステップ候補を短くまとめる。

ユーザーが分割を承認するまで、調整を繰り返す。途中終了を分割の承認として扱わない。分割案や成果物のチケット一覧は複数項目を含めてよい。

### 5. 設定済みの課題管理先にチケットを公開する

承認された分割について、対象範囲の未決・文書の食い違いがないことを再確認してから公開する。各票に受け入れ条件・対象外・関連要求の出典を記載し、計画がなくても単体で理解できるようにする。再実行時は既存票・コメント・完了条件を読み、同じ票の無条件な作り直しや再採番を行わず、更新対象と追加分を区別する。**方法**は、`/setup-matt-pocock-skills` で設定した課題管理先によって異なる。チケット自体は同じで、変わるのは依存関係の表現だけである。

- **ローカルファイル** → `docs/work/YYYY-MM-DD-NN-<work-slug>/issues/<NN>-<slug>.md` に、チケットごとに1ファイルを書く。初回は依存順（前提となるものが先）に `01` から番号を付ける。追加分は既存最大番号の次を使い、着手順は `Blocked by` で判断する。作業フォルダーは保存規約に従って特定・必要時作成する。各ファイルの "Blocked by" に、同じ作業内の依存チケットの番号／タイトルを列挙する。別作業の依存先には作業フォルダーを特定できる文書リンクを使う。以下のチケット単位のテンプレートを使う。必ず1チケットにつき1ファイルとし、1つのファイルにまとめない。
- **専用の課題管理サービス（GitHub、Linearなど）** → 依存順（前提となるものが先）に、チケットごとに1つの課題を公開する。これにより、依存関係で実在する識別子を参照できる。そのサービスに標準の依存関係／子課題の仕組みがあれば使い、なければ各チケットの "Blocked by" に前提となる課題を設定する。別の指示がなければ、`ready-for-agent` のトリアージラベルを付ける。チケットは、その構成自体がエージェントの着手に適したものになっている。

**着手可能な項目（frontier）**を進める。依存先がすべて完了したチケットである。完全に直列の依存関係なら、上から下へ進める。

保存時は課題管理規約に従って更新日時も変更する。保存後に各票の内容を読み戻し、出典リンクと依存先は課題管理規約に従って出力文書の位置から解決し、実在を確認する。その後、実際の作業フォルダーと成果物のリンクを返す。部分失敗は保存済み・未保存を示し、完了と伝えない。Planモードでは案だけを示し、未保存と明記する。

親の課題を閉じたり変更したりしてはならない。

どちらの形式でも、実装コードの具体的なファイルパスやコードの断片は、すぐに古くなるため避ける。要求・計画・課題などの文書リンクは出典として記載する。例外：試作によって、文章より正確に判断を表すコードの断片ができた場合（状態遷移、状態更新処理であるreducer、schema、型の構造）は、直接記載し、試作に由来することを短く示す。動くデモ全体ではなく、判断を表す重要な部分だけに絞る。
