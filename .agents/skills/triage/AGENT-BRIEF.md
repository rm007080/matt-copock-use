# エージェントブリーフの書き方

エージェントブリーフは、課題が `ready-for-agent` に移るときにGitHubの課題またはPR（プルリクエスト）へ投稿する、構造化されたコメントです。これはAFK（away from keyboard、離席中にエージェントだけで進める）エージェントが作業する、作業の正本となる仕様です。元の本文と議論はコンテキストであり、エージェントブリーフが契約になります。

ブリーフは**エージェントが何をすべきか**を述べます。これは2つの表面にまたがります。課題なら何もないところから変更を構築すること、PRなら**既存の差分に対して**残った作業（仕上げ、抜けの解消、レビュー指摘への対応）です。どちらにも同じ原則を使いますが、下のPR例で違いを示します。

## 原則

### 精密さより持続性

課題が `ready-for-agent` に数日または数週間置かれることがあります。その間にコードベースは変わります。ファイルの名前変更、移動、リファクタリングがあっても役立つようにブリーフを書きます。

- **行う**：interface（インターフェース）、型、振る舞いの契約を説明する
- **行う**：エージェントが探す、または変更するべき具体的な型、関数シグネチャ、設定の形を挙げる
- **しない**：ファイルパスを参照する（古くなるため）
- **しない**：行番号を参照する
- **しない**：現在の implementation（実装）構造が残ると仮定する

### 手順ではなく振る舞い

**どう実装するか**ではなく、システムが**何をすべきか**を説明します。エージェントはコードベースを新たに探索し、自分で実装上の判断をします。

- **良い例:** 「`SkillConfig` 型は、`CronExpression` 型の任意の `schedule` フィールドを受け入れるべき」
- **悪い例:** 「`src/types/skill.ts` を開き、42行目に schedule フィールドを追加する」
- **良い例:** 「ユーザーが引数なしで `/triage` を実行したら、注意が必要な課題の概要を表示する」
- **悪い例:** 「メインハンドラー関数にswitch文を追加する」

### 完全な受け入れ条件

エージェントは、いつ完了したかを知る必要があります。すべてのエージェントブリーフには、具体的でテスト可能な受け入れ条件が必要です。各条件は単独で検証できなければなりません。

- **良い例:** 「`gh issue list --label needs-triage` を実行すると、初回分類を通過した課題が返る」
- **悪い例:** 「トリアージが正しく動く」

### 明示的な範囲の境界

範囲外を明記します。これにより、エージェントが隣接機能を過剰に作り込んだり、仮定したりするのを防ぎます。

## テンプレート

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** 必要な作業を1行で説明する

**Current behavior:**
現在何が起きているかを説明する。バグの場合は壊れている振る舞いを書く。
機能拡張の場合は、その機能が前提とする現状を書く。

**Desired behavior:**
エージェントの作業が完了した後に何が起きるべきかを説明する。
境界ケースとエラー条件を具体的にする。

**Key interfaces:**
- `TypeName`: 何を変更する必要があり、なぜ変更するのか
- `functionName()` の戻り値の型: 現在返しているものと、返すべきもの
- 設定の構造: 新たに必要な設定オプションの形

**Acceptance criteria:**
- [ ] 具体的でテスト可能な条件1
- [ ] 具体的でテスト可能な条件2
- [ ] 具体的でテスト可能な条件3

**Out of scope:**
- この課題で変更または対応してはならないもの
- 関係がありそうに見えるが別の機能であるもの
```

## 例

### 良いエージェントブリーフ（バグ）

```markdown
## Agent Brief

**Category:** bug
**Summary:** スキルの説明が単語の途中で切れ、壊れた出力になる

**Current behavior:**
スキルの説明が1024文字を超えると、単語の境界に関係なく正確に
1024文字で切り詰められる。その結果、説明が単語の途中で終わる
（例："Use when the user wants to confi"）。

**Desired behavior:**
切り詰めは1024文字より前にある最後の単語境界で行い、
切り詰められたことを示すために「...」を追加する。

**Key interfaces:**
- `SkillMetadata` 型の `description` フィールド：型の変更は不要だが、値を設定する検証・処理ロジックは単語境界を尊重する必要がある
- SKILL.md のフロントマターを読み、説明を抽出する任意の関数

**Acceptance criteria:**
- [ ] 1024文字未満の説明は変更されない
- [ ] 1024文字を超える説明は、1024文字より前の最後の単語境界で切り詰められる
- [ ] 切り詰められた説明は「...」で終わる
- [ ] 「...」を含む全体の長さは1024文字を超えない

**Out of scope:**
- 1024文字という上限自体の変更
- 複数行の説明への対応
```

### 良いエージェントブリーフ（機能拡張）

```markdown
## Agent Brief

**Category:** enhancement
**Summary:** 却下した機能要望を追跡する `.out-of-scope/` ディレクトリ対応を追加する

**Current behavior:**
機能要望を却下すると、課題を `wontfix` ラベルで閉じ、コメントを付ける。決定や理由を永続的に記録する場所はない。
今後、似た要望が来るたびに、メンテナーは過去の議論を思い出すか検索する必要がある。

**Desired behavior:**
却下した機能要望を `.out-of-scope/<concept>.md` ファイルに記録する。ファイルには、決定、理由、その機能を要望したすべての課題へのリンクを含める。新しい課題をトリアージするときは、これらのファイルを照合する。

**Key interfaces:**
- `.out-of-scope/` のMarkdownファイル形式：各ファイルには `# Concept Name` 見出し、`**Decision:**` 行、`**Reason:**` 行、課題リンクを並べる `**Prior requests:**` リストを置く
- トリアージワークフローは早い段階で `.out-of-scope/*.md` をすべて読み、概念の類似性によって受信した課題と照合する

**Acceptance criteria:**
- [ ] 機能をwontfixとして閉じると、`.out-of-scope/` にファイルが作成または更新される
- [ ] ファイルに、決定、理由、閉じた課題へのリンクが含まれる
- [ ] 一致する `.out-of-scope/` ファイルがすでにある場合、新しい課題は重複ファイルを作らず、その「Prior requests」リストに追加される
- [ ] トリアージ中、既存の `.out-of-scope/` ファイルが確認され、新しい課題が過去の却下に一致すると示される

**Out of scope:**
- 自動照合（人間が一致を確認する）
- 以前に却下した機能の再開
- バグ報告（`.out-of-scope/` に送るのは機能拡張の却下だけ）
```

### 良いエージェントブリーフ（PR）

PRの場合、「Current behavior」は差分の状態を説明し、ブリーフはゼロから構築するのではなく、差分を仕上げるか修正するようエージェントに依頼します。

```markdown
## Agent Brief

**Category:** enhancement
**Summary:** `triage list` の投稿者による `--json` 出力フラグを完成させる

**Current behavior:**
PRは課題一覧をJSONにシリアライズする `--json` フラグを追加する。正常系は動作し、差分はプロジェクトのコマンド構造に合っている。2つの抜けが残っている。エラーが人間向けのテキスト（JSONではない）で出力され、新しいフラグにテストカバレッジがない。

**Desired behavior:**
`--json` を指定した場合、エラーを含むすべての出力が標準出力上の正しいJSONになり、コマンドの終了コードは変わらない。フラグがない場合、既存の人間向け出力はそのままにする。

**Key interfaces:**
- コマンドのエラーパスは `--json` の下で、プレーンテキストのエラーの代わりに `{ "error": string }` を出力する
- PRがすでに追加した既存のシリアライザーを再利用し、2つ目を導入しない

**Acceptance criteria:**
- [ ] `triage list --json` は成功時とエラー時の両方で正しいJSONを出力する
- [ ] 終了コードはJSONではないコマンドと一致する
- [ ] `--json` の成功出力と1つのエラーケースをテストでカバーする
- [ ] デフォルト（JSONではない）出力はバイト単位で変更されない

**Out of scope:**
- 他のコマンドへの `--json` 追加
- PRがすでに定義した成功ペイロードのJSON形状の変更
```

### 悪いエージェントブリーフ

```markdown
## Agent Brief

**Summary:** トリアージのバグを直す

**What to do:**
トリアージの何かが壊れている。メインファイルを見て直すこと。
150行目付近の関数に問題がある。

**Files to change:**
- src/triage/handler.ts (150行目)
- src/types.ts (42行目)
```

これは悪い例です。次の問題があります。

- カテゴリがない
- 「トリアージの何かが壊れている」という曖昧な説明
- いずれ古くなるファイルパスと行番号を参照している
- 受け入れ条件がない
- 範囲の境界がない
- 現在の振る舞いと望ましい振る舞いの説明がない
