# 範囲外ナレッジベース

リポジトリの `.out-of-scope/` ディレクトリには、却下した機能要望の記録を永続的に保存します。目的は2つあります。

1. **組織の記憶**：課題を閉じた後も推論を失わないよう、機能を却下した理由を残す
2. **重複排除**：過去の却下と一致する新しい課題が来たとき、再び議論する代わりに過去の決定をスキルが示せるようにする

## ディレクトリ構成

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

課題ごとではなく、**概念**ごとに1ファイルを作ります。同じものを求める複数の課題は1つのファイルにまとめます。

## ファイル形式

ファイルはデータベースのエントリではなく、短い設計文書のような、緩やかで読みやすい形式にします。初めて読む人にも理由が明確で役立つよう、段落、コードサンプル、例を使います。

```markdown
# ダークモード

このプロジェクトはダークモードやユーザー向けのテーマ設定に対応していない。

## 範囲外である理由

レンダリングパイプラインは、`ThemeConfig` で定義された単一のカラーパレットを前提としている。複数のテーマをサポートするには、次が必要になる。

- コンポーネントツリー全体をラップするテーマコンテキストプロバイダー
- コンポーネントごとのテーマ対応スタイル解決
- ユーザーのテーマ設定を永続化する層

これは、プロジェクトがコンテンツ作成に集中する方針に合わない、大きなアーキテクチャ変更になる。テーマ設定は、出力を埋め込んだり再配布したりする下流の利用者が扱う関心事である。

```ts
// 現在のThemeConfig interface（インターフェース）は実行時の切り替え用に設計されていない：
interface ThemeConfig {
  colors: ColorPalette; // 単一のパレット。ビルド時に解決される
  fonts: FontStack;
}
```

## Prior requests

- #42: "ダークモードに対応する"
- #87: "アクセシビリティ向けのナイトテーマ"
- #134: "ダークテーマのオプション"
```

### ファイル名を付ける

概念を表す短く説明的なkebab-case名を使います。`dark-mode.md`、`plugin-system.md`、`graphql-api.md` のような名前です。ディレクトリを見ている人がファイルを開かなくても何が却下されたか理解できる程度に、認識しやすい名前にします。

### 理由を書く

理由は実質的なものにします。「望んでいないから」ではなく、なぜなのかを書きます。良い理由では次を参照します。

- プロジェクトの範囲や思想（「このプロジェクトはXに集中し、テーマ設定は下流の関心事である」）
- 技術的制約（「これをサポートするとYが必要になり、Zのアーキテクチャと衝突する」）
- 戦略上の決定（「BではなくAを使うことにした。なぜなら…」）

理由は長く役立つものにします。「今は忙しすぎる」のような一時的な事情は避けます。それは本当の却下ではなく、延期だからです。

## `.out-of-scope/` を確認するタイミング

トリアージ（ステップ1：コンテキストを集める）では、`.out-of-scope/` 内のすべてのファイルを読みます。新しい課題を評価するときは、次を確認します。

- 依頼が既存の範囲外の概念に一致するか
- キーワードではなく概念の類似性で一致させる。「ナイトテーマ」は `dark-mode.md` に一致する
- 一致したら、メンテナーに示す。「これは `.out-of-scope/dark-mode.md` に似ています。以前、[理由]で却下しました。今も同じ考えですか？」

メンテナーは次のいずれかを行えます。

- **確認**：新しい課題を既存ファイルの「Prior requests」リストに追加して閉じる
- **再考**：範囲外ファイルを削除または更新し、課題を通常のトリアージへ進める
- **異議あり**：課題は関連しているが別物なので、通常のトリアージへ進める

## `.out-of-scope/` に書くタイミング

**機能拡張**（バグではないもの）を `wontfix` として**却下**したときだけ書きます。これは課題と同様に機能拡張PR（プルリクエスト）にも適用されます。却下されたPRもここに記録し、同じ依頼が新しいコードとして戻らないようにします。

**すでに実装済み**であるために `wontfix` として閉じる場合は、ここに書かないでください。これは構築済みの機能であり、却下されたものではありません。記録すると重複チェックを誤った却下で汚染します。代わりに、終了コメントで機能がすでに存在する場所を指します。

流れは次のとおりです。

1. メンテナーが機能要望を範囲外と判断する
2. 一致する `.out-of-scope/` ファイルがすでにあるか確認する
3. ある場合：新しい課題を「Prior requests」リストに追加する
4. ない場合：概念名、決定、理由、最初の過去リクエストを含む新しいファイルを作る
5. 決定を説明し、`.out-of-scope/` ファイルに言及するコメントを課題へ投稿する
6. `wontfix` ラベルで課題を閉じる

## 範囲外ファイルを更新または削除する

メンテナーが以前に却下した概念について考えを変えた場合は、次のようにします。

- `.out-of-scope/` ファイルを削除する
- スキルは古い課題を再開する必要がない。それらは履歴記録である
- 再考のきっかけとなった新しい課題は、通常のトリアージへ進む
