### to-readme の手順

1. **対象を特定する。** ユーザーの指定と作業場所から対象プロジェクト・README を特定し、そのプロジェクトの指示と既存 README を読む。複数候補から特定できない場合だけ確認する。既存の言語・構成や明示された形式を尊重する。
2. **根拠を集める。** 目的・主要機能・導入条件・利用開始方法に必要なコード、設定、実行入口、資料を読む。仕様書、用語集、課題管理設定の不在を理由に、別スキルの実行や文書の先行作成を要求しない。対象外プロジェクトの事実を持ち込まない。
3. **重要な不足を確認する。** 調べて分かることは質問しない。基本利用の説明を左右する未確定事項や矛盾が残る場合は1問ずつ確認し、回答後に次の確認を選び直す。軽微な掲載項目を埋めるためだけに質問を続けない。
4. **新規作成または更新する。** 概要・用途・前提条件・導入・基本利用・関連資料へのリンクを基本とし、対象に合う項目だけを採用する。固定見出しの穴埋めにはしない。既存 README は有効な説明・人の編集・関連リンクを保持し、必要な箇所を変更する。
5. **内容と保存を確認する。** コマンドの根拠、参照ファイル、リンク、機能の実装状態を確かめ、保存後に読み戻す。実行していないコマンドを実行確認済みとしない。重要な矛盾は勝手に決着させない。
6. **結果を返す。** 作成・更新した README、確認した内容、未検証事項を報告する。保存失敗や重要情報の回答待ちは未完了として扱う。

`wizard` などで作られた導入手順が存在する場合は、README からの有効なリンクを保持・確認する。詳細な仕様や手順の長い複製を増やすより、概要と参照先を示す。

### 適用設定

- `SKILL.md` の先頭の設定に `name: to-readme` と、README の作成・更新を対象にする簡潔な `description` を置く。
- `disable-model-invocation: true` は付けない。通常の README 依頼で適用できる設定とする。
- `agents/openai.yaml` は既存の表示形式に合わせ、`interface.display_name` と `interface.short_description` を設定する。表示名は `To Readme` とする。
- `policy.allow_implicit_invocation` は `true` と明記する。この値は、名前を指定しない依頼への自動適用を許可する設定である。
- README を読むだけの依頼、仕様書だけの作成、一般的なコード編集を、README の作成・更新依頼として扱わない。既存スキルを自動的に連続実行する仕組みは追加しない。

### 規約と案内の変更

両方の `domain.md` に、README は利用者が概要・価値・導入・基本利用を理解する案内であり、合意した要求・構成・技術選定の管理先を置き換えないことを短く記載する。「全体文書」の同期契約が指す対象は、既存の `docs/spec.md`・`docs/architecture.md`・`docs/tech-stack.md` の3文書と明記する。

README を既存の同期対象に追加せず、`to-spec` の成果物にも追加しない。配布用のひな形にある単一・複数の文脈の説明は保持する。この変更だけではセットアップ本体や `AGENTS.md` の案内の書き換えは必要ない。

`ask-matt` には単独で使えるエージェントスキルとして追記する。地図には「README を作成・更新したい」という地点を「地図の外」に追加し、既存の `details` と `name="walk"` の構造を使う。3項目の内容は、対象と重要な不足への回答、作成・更新する README、根拠・保存・残る未検証事項を確認した終了状態とする。表示する説明は既存カードと同程度に短くする。

V1〜V4では実際の出力または質問を確認する。V5〜V6は、検証対象のスキルを事前に強制適用した状態では確認済みとしない。実行環境から選択状況を確認できない場合は、設定と説明の確認結果、および実際の適用が未検証であることを分けて報告する。これらの未検証を残したまま全体の検証完了とはしない。

検証で使った入力、出力や質問の要点、結果は本計画に簡潔に追記する。新しい失敗や未解決の懸念がない限り、同じ検証を繰り返したり対象を拡張したりしない。
